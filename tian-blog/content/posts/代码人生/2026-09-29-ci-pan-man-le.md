服务器上有一类故障特别讨厌：它不给你报错，只给你结果不对。

程序照常启动，定时任务照常触发，接口照常返回 200，日志照常往里写——直到某一天，一个一直好好跑着的脚本突然失败了，报的错还很奇怪：文件写不进去、数据库锁不住、临时文件创建不了。你去查业务逻辑，查半天查不出问题，因为问题根本不在业务逻辑里。

十有八九，是磁盘满了。

## 一种不会提前打招呼的资源

CPU 不够用的时候你会立刻知道：接口变慢、机器发烫、`load` 飙到十几。内存不够用的时候你也会知道：进程被杀，`dmesg` 里躺着 OOM Killer 留下的记录，写得明明白白。

磁盘不一样。

磁盘空间是可以被慢慢耗光的——每天几百兆，安安静静，没有任何一个环节会因为它而变慢。它不影响性能，不影响响应时间，不影响你的监控曲线。它甚至不影响你部署：你照样能 git pull、照样能重启服务，因为那些文件都很小。

于是它就成了唯一一种"你不到最后一刻感觉不到"的资源。而等到你感觉到的时候，通常已经不是一个"提醒"，而是一次失败。

最讽刺的是失败的方式。很多语言里，往文件写日志的调用是"尽力而为"的：能写就写，写不进去就算了，不抛异常。设计者的逻辑是善良的——日志不该拖垮主流程。可结果就是，磁盘满的那段时间里，你的日志悄悄变成空的。你以为自己在记录，其实什么都没留下。等你想查当时发生了什么，日志里一片空白——故障现场被故障本身抹掉了。

这才是磁盘满真正麻烦的地方：**它先让你失去取证能力，再让你面对一个没有证据的问题。**

## 先看清"谁在长"

我现在的习惯是，只要碰到任何"莫名其妙写不进去"的问题，第一件事不是看代码，是两条命令。

第一条：

```bash
df -h
```

它告诉你每个挂载点的总容量、已用、可用、使用率。一眼就能看出是不是某个分区顶到 100% 了。顺便说一句，看的时候别只看根目录——如果数据在单独挂载的盘上（比如我这儿 `/data` 是一块独立的盘），根目录空着跟你的程序没关系。

第二条，比第一条少有人用：

```bash
df -i
```

`-i` 看的是 inode，不是空间。文件系统的 inode 总数是固定的，每创建一个文件（或者目录、软链接）就占用一个。这意味着一种非常反直觉的情况：**空间还剩几十 G，你却再也创建不了任何文件。** 因为 inode 用光了。

什么情况下会把 inode 用光？不是大文件，恰恰是海量的小文件。一天几万条的缓存文件、一个没清理的 session 目录、某次死循环留下的碎片——它们每个只占几 KB，但它们每个都吃掉一个 inode。这种现象在"空间明明够"的时候出现，会让你彻底懵掉，因为你脑子里"满了"这个概念是绑在容量上的。

确认了是空间问题，再定位是谁吃的：

```bash
du -h --max-depth=1 /data | sort -h
```

`--max-depth` 限制只统计下一层，`sort -h` 按人类可读的大小排序（别用 `sort -n`，`-h` 才懂 `2.3G` 比 `900M` 大）。一层一层往下扎，大头很快就露出来。十次里有九次，第一名是日志目录，第二名是某个备份，第三名是你以为早就删掉的临时文件。

## 删了文件，空间没回来

下面这个坑，第一次遇到能让人怀疑人生。

你 `du` 出来一个大文件，`rm` 掉，回头看 `df -h`——**使用率一点没变。**

文件明明删了，`ls` 也看不到了，空间却还在被占着。原因在于：Linux 里删一个文件，删掉的只是"目录里的那个名字"。如果此时还有进程打开着这个文件，文件的数据块不会释放，一直到那个进程关闭句柄或者退出为止。

也就是说，一个跑了半年的服务，可能至今都攥着一个你三小时前就已经"删掉"的日志文件。你在文件系统里看不到它，但它实实在在占着你的盘。

这事的证据在 `lsof` 里：

```bash
lsof +L1
```

`+L1` 是"link count 小于 1"，也就是链接数为零——名字已经不在目录里了、但句柄还在的那些文件。跑一下，你会看到一堆 `(deleted)` 的条目：有的是系统自己的东西，无关紧要；但如果有某个进程占着一个几 G 的 `(deleted)` 文件，那它就是你要找的答案。

解法有两种：重启那个进程，让它把句柄放开；或者在不重启的前提下，用 `: > /proc/<pid>/fd/<fd>` 把文件内容清空——因为句柄还在，这个"文件"仍然是可写的，只是你从目录里找不到它。前者干净，后者救急。

这也解释了我为什么对"直接 rm 大日志"这个操作一直很警惕：删的名字没了，占的空间还在，你以为问题解决了，其实什么都没变——唯一的区别是你把证据也一起弄丢了。

## 真正的解法是"知道谁在长"

清理是亡羊补牢。定期清理更糟一点，因为它给人一种"我管了"的错觉。

真正管用的只有一件事：**让每一个会增长的东西，都有一个被明确安排好的出路。**

日志是最典型的。日志文件必须轮转——到多大就切一份、留几份、旧的压缩还是删除，这些是要写在配置里的，而不是等它涨到 10G 再手动 `rm`。系统自带的 `logrotate` 就是干这个的，配置两行就够；自己写的脚本往文件里追加日志的，就在脚本里自己判断大小。关键不在于用哪个工具，而在于"增长"这件事是被设计的，不是被放任的。

还有几类东西同样需要有人看着：数据库文件（只增不减的表、临时文件、WAL）、包管理器的缓存（`pip`、`apt`、`npm` 的缓存目录经常是隐藏的巨无霸）、容器镜像和它留下的分层、以及 `/tmp`——很多程序默认把临时中间结果丢在这儿，正常退出会清理，异常退出的就永远留下了。

最后一条，也是最重要的一条：把磁盘使用率当成一个正经指标，配上阈值告警。80% 就该响一次，90% 就该响得难听一点。留那些余量不是因为用得上，是因为**磁盘满这件事没有缓冲区——它一满，所有需要写盘的操作同时开始失败，你没有任何一步可以退。**

## 它攒着你所有的"以后再说"

我很喜欢磁盘这个资源的一点，是它特别诚实。

CPU 会说谎，你的程序可能在用 5% 的 CPU 假装自己很忙；内存会说谎，缓存可以占着几十 G 却毫无用处；网络会说谎，超时可能是对端的问题，也可能是你自己的。只有磁盘，占用就是占用，一个字节一个字节，全是你自己放进去的。

它只是慢慢填满。所有那些"先这样，以后再清理"的临时文件、"先留着，万一有用"的旧备份、"先不加限制"的日志——它都统统替你攒着，一样不落。攒到某个你毫无防备的早上，一次普通的写入失败。

所以我现在会时不时看它一眼，不是因为我勤快，是因为我知道它从来不提醒，只是记账。
