# 0.1 加 0.2 不等于 0.3：计算机里的数字是一笔约数

前阵子写一个统计脚本，算几个目录占磁盘的比例。三段加起来应该是 1，打印出来是 `0.9999999999999999`。我盯着这行看了几秒，第一反应是自己逻辑写错了，把三行求和改了两遍，系数没动，结果一模一样。

打开解释器敲了一下，更离谱的事出来了：

```
>>> 0.1 + 0.2
0.30000000000000004
```

不是我的代码有问题，是我对"计算机里的数字"这件事，一直有个错误的想象。我以为 `0.1` 在机器里就是零点一，事实是它从来都不是。

## 那个 3 是哪来的

十进制里我们习惯分母是 10、100、1000，写成小数一位一位往下排。二进制只认 2、4、8、16 这些分母，所以 `1/2`、`1/4`、`1/8` 是干净的，`1/10` 不是——十里面有个 5，5 在二进制里除不尽。

`0.1` 换成二进制是 `0.00011001100110011...`，那个 `0011` 无限循环下去，跟你用十进制写 `1/3` 得到 `0.3333...` 是一个道理。差别在于：十进制的 `1/3` 你早就认了，知道写不完就四舍五入；而二进制的 `0.1` 写不完这件事，平时没人跟你说，你就当它写完了。

机器存不下无限长，只能截断到固定长度。Python 的浮点数（也就是 IEEE 754 双精度）用 64 个二进制位：1 位符号、11 位指数、52 位尾数。52 位尾数提供大约 15 到 17 位有效十进制数字，看起来很多，可它截断的位置不是我们能挑的。

所以 `0.1` 被存成的真实值是：

```
>>> from decimal import Decimal
>>> Decimal(0.1)
Decimal('0.1000000000000000055511151231257827021181583404541015625')
```

比 0.1 大了一点点，那个差值小得看不见，但它一直在。`0.2` 也差一点点。两个都偏一点的东西加在一起，偏的量露了出来，就是那个 `4`。

这就是我看到的核心：**浮点数不是"数"，是一笔约数。** 它像个只肯记 15 位有效数字的会计，后面全按"大概齐"记，你不问它就不说。

## 约数会累积，也会互相吃掉

单次误差小到无所谓，可它是会攒的。

```
>>> sum([0.1] * 10000)
1000.0000000001588
```

一万个 0.1，理论上正好一千，实际多了一亿五千万分之一。做一次加法无所谓，做一亿次加法就是事故。金额结算、计费、累计统计，恰恰都是一亿次加法那一类。

还有一种更隐蔽的：大数吃小数。

```
>>> 1e16 + 1 == 1e16
True
```

十六位数以下的小数点后信息，尾数根本装不下，`+1` 直接被丢掉，而且不报任何错。你以为加了一，其实什么都没发生。

`round` 也会背叛直觉：

```
>>> round(2.675, 2)
2.67
```

看着像 bug，其实不是。`2.675` 在机器里存的是 `2.67499999999999982...`，它老老实实四舍五入，得到 2.67。是前面那笔约数的问题，不是舍入函数的问题。

至于 `float('nan') != float('nan')` 返回 `True`，`0.1 + 0.7 == 0.8` 返回 `False` 这类事，都是同一个根子：你在用一个近似值问它要不要完全相等，它只能给你一个近似值该给的答案。

## 知道它是约数，就知道哪些地方不能用在它身上

这些坑的解法不用背，只要认下"这是笔约数"，后面的选择就顺了。

**钱不要用浮点数。** 存整数分，19.99 存成 1999，前端显示的时候再除。数据库用 `DECIMAL`，Python 用 `Decimal('0.1')`——注意必须用字符串构造，`Decimal(0.1)` 会先把 0.1 翻译成那个长长的小数，把误差原样搬进精确类型里，白忙一场。

**不要用 `==` 比浮点数。** 用容差，`abs(a - b) < 1e-9`，标准库里有 `math.isclose`。测试里断言浮点结果相等，是最容易埋雷的一行。

**中间过程不要四舍五入，只在显示时格式化。** 很多人为了让数字好看，每一步都 round 一下，误差一路放大。数字该多脏就多脏地算完，最后 `f'{x:.2f}'` 一次性收尾。这一点我踩过：报表上每一行都保留两位看着整齐，合计对不上明细，查了半天是每一步都截了。

**求和顺序会影响结果。** 一堆大小悬殊的数相加，先把小的加一起再加大的，误差明显小；真要精确，标准库的 `math.fsum` 是按补偿算法做的，比 `sum` 稳。

## 它没错，是我们借了账本

我后来想，这件事别扭在哪。别扭在我把十进制世界里的直觉，原封不动搬进了二进制世界。十进制里 0.1 是一个可以写出来的符号，二进制里它写不出来，就这么简单。不是机器算错了，是它按自己的进制记账，而我从来没问过它怎么记。

同样的道理，`0.1 + 0.2` 这个例子里真正值钱的不是那个 `0.30000000000000004`，而是它提醒我：任何一层抽象都有它自己的精度，你信它，就得知道它信到哪一位为止。磁盘容量信到 4K 一页、时间信到毫秒、`float` 信到 15 位有效数字——再往下问，它就开始给你编了。

所以现在写代码，我会先问一句：这个数字是用来算的，还是用来给人看的？给人看的，算完再打扮；用来算的，选一个它不会撒谎的存法。十五位有效数字够不够用，我自己心里得有数，而不是等它对不上账那天，才回头怀疑逻辑。
