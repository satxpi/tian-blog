# 哈希不是加密，它是一枚只能往前盖的章

下载一个安装包，旁边常常挂着长长一串字母数字，让你核对。很多人（包括几年前的我）会把它理解成"加密后的文件"，觉得这串东西是用来防别人偷看的。它确实有用，但用处完全不是那个方向。

在这台机器上敲几条命令，事情就清楚了。

```bash
$ printf 'hello' > a.txt
$ printf 'hello!' > b.txt
$ printf 'helLo' > c.txt

$ sha256sum a.txt b.txt c.txt
2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824  a.txt
ce06092fb948d9ffac7d1a376e404b26b7575bcc11ee05a4615fef4fec3a308b  b.txt
0c2d7e3bbd9cdbbaa3d18a39ac01dc79202c0769db50069b86b81b4aea639271  c.txt
```

三个文件，内容是 `hello`、`hello!`、`helLo`，长度只差一两个字节。三枚指纹却毫无相似之处，从头到尾没有一个字符是"渐变"过去的。这就是哈希的第一条脾气：输入动一根头发，输出整张脸都换。

第二条脾气藏在长度里。`hello` 是 5 个字节，一个 4G 的电影是几十亿个字节，两者的 SHA-256 结果都是 64 个十六进制字符，一个字不多，一个字不少。它把任意长的东西压成固定长度的一小段。

这两条加起来，指向一个最关键的性质：**哈希只能往前算，不能往回走。**

给定文件算指纹，一秒钟的事；给定指纹想还原文件，没有"钥匙"这回事。加密是有钥匙的：锁上,钥匙在手,还能开回来;哈希是从头到尾就把过程碾碎了,剩下的那串东西只是"这个输入存在过"的证据,不是"这个输入的备份"。

我早年犯过的错，就错在这里：把哈希当成一种"加密存储"，以为数据库里那一列密码哪天需要了还能"解"出来。实际上根本解不出来，也不需要解——系统从来不需要知道你的密码原文，它只需要核对"你这次输入的指纹，和当初存下的那枚是不是同一枚"。你输对了，指纹一致，放行；输错了，指纹不一致，拒绝。整个过程里，密码原文连一秒钟都没被保存过，这是好事。

但好事里有坑，坑在"同一枚指纹"这四个字上。

哈希是确定性的：同样的输入，永远出同样的输出。这对校验文件是优点——你下载的文件算出来跟官网那串一致，就说明运输途中没被改过。可对密码就是缺点了：两个人碰巧用了同一个密码，数据库里存的就是同一个值；而无盐的 `sha256("123456")`，在任何一台机器上算出来都长这样：

```
8d969eef6ecad3c2...
```

不需要破解，因为早有人把常见密码预先算好，做成一张巨大的对照表。拿到你的指纹，查表就查回原文。所谓"破解密码"，大多数时候不是算出来的，是查出来的。

对付查表，办法是加盐：给每个用户的密码后面拼一段随机字符串再算，盐跟指纹一起存。盐不需要保密，它只需要不一样。

```python
hashlib.pbkdf2_hmac('sha256', b'123456', b'aaa', 100000).hex()[:16]
# 6fa6db109f906c18

hashlib.pbkdf2_hmac('sha256', b'123456', b'bbb', 100000).hex()[:16]
# 35e4a505cbef7b3c
```

同一个密码 `123456`，换一段盐，指纹就完全不同。攻击者没法预先造表了，只能针对你一个人硬算。到这里，"慢"才成了武器。哈希函数本身有快有慢，加密用的 SHA-256 快到每秒能算上亿次，这对存密码是灾难；专门给密码设计的 PBKDF2、bcrypt、Argon2 会故意把过程拉长。我在这台机器上实测：

```
迭代 1 次        0.0 ms
迭代 1000 次     0.2 ms
迭代 10 万次    20.3 ms
迭代 60 万次   121.8 ms
```

`121.8` 毫秒，你登录一次感觉不到，机器一天验证几万次也就多花几分钟。可对小偷来说，他原本一秒能试上亿个密码，现在一秒钟只能试八个。成本从"按秒"变成"按年"，密码这件事才算勉强站住了。

哈希还有个比密码更低调的用途：去重。十几万张照片要备份，怎么知道哪几张是重复的？不用一张张打开看，算指纹，指纹相同的归一堆。我在服务器上整理旧数据时就是用这个笨办法，几秒钟扫完几万个文件，同一份文件复制过三次四次的情况一目了然。这里哈希当的是"索引"，连安全都算不上，纯纯的省事。

不过指纹相同，真的就等于内容相同吗？理论上不一定。哈希是把无限多的输入塞进有限长度的输出里，碰撞（两个不同输入算出同一个值）在数学上必然存在，只是概率低到可以忽略。低到什么程度，取决于算法有多"结实"，而结实这件事是会过期的。

MD5 曾经是标准，输出 32 个字符，早年到处都在用。2004 年，王小云团队给出了能在很短时间内构造 MD5 碰撞的方法；2017 年，Google 和 CWI 又公开了一份 SHA-1 的实际碰撞文件，两个内容不同的 PDF，SHA-1 完全一样。这两个事说明的是同一件事：**哈希的安全性不写在它的长度上，而写在它抵抗碰撞的能力上。** 而抵抗能力会随着算力和研究一起贬值。所以现在的规矩很朴素：新东西别用 MD5 和 SHA-1，校验文件用 SHA-256，存密码用专门为密码设计的慢哈希。

绕了一圈，其实只想讲一个判断方法。

遇到一个陌生的工具，先别急着问"它能干什么"，先问一句：**它能不能倒着走。**

能倒着走的，是锁，用法是保管和还原，责任在钥匙上，钥匙丢了就完了。不能倒着走的，是指纹和印章，用法是比对和证明，责任在"你当初盖的是哪一枚"，重点不是藏，而是对得上。这两种东西长得像——都是一串看不懂的字符，都让人有种"已经加密了"的安心感——但方向相反，责任也相反。把它们搞混，前一种会让你以为丢了钥匙还能撬开，后一种会让你以为盖了章的东西不能外泄。

哈希从来不是加密，它是往前走就回不来的那一步。想清楚这一点，很多"为什么不能解密"的困惑就自己散了。
