早上七点半，我打开电脑想看看昨晚那个批处理任务跑出来的结果文件——最后修改时间是三天前。也就是说，它已经连续三个晚上什么都没干了，而且没告诉我。

我在终端里把同一条命令手动敲了一遍，十秒钟跑完，一切正常，输出文件乖乖躺在那儿。

这大概是自动化里最气人的一种故障：**手动跑没事**。你甚至会开始怀疑是机器累了、是运气。但真相通常朴素得多——脚本没变，变的是它被放进去的那个环境。

我们的默认想法是：定时任务不就是"换个时间执行同一个脚本"吗？不是。你写 crontab 那一刻，等于把脚本从"你的终端"搬进了"一个没有你的房间"。终端里有你攒了三年的 PATH、有你的工作目录、有 .bashrc 里那几行 export、有你的眼睛盯着屏幕、有命令结束时那个 exit code。那个房间里这些东西全都没有，只有 cron 自己的缺省值。脚本还是那个脚本，房子整个换了。

先把最常见的一层说清楚：**命令找不到**。cron 启动任务时给的 PATH 通常只有 `/usr/bin:/bin`。而我平时用的 python3 其实在别的地方——装依赖时装进去的那些 bin 目录，终端里之所以能用，是因为 `.bashrc` 在我每次开 shell 时替我把路径加上了。cron 不读 `.bashrc`，它不认你这个人。于是同一个 `python3 脚本.py`，在我手里是正常执行，在 cron 手里是 `command not found`，然后把这条错误安静地扔掉。

所以我现在写 crontab，风格很难看但很省事：每一行都长着一串绝对路径，`/usr/bin/python3 /data/xxx/run.py`。同时在文件顶部写一行 `PATH=/usr/local/bin:/usr/bin:/bin`。丑是丑，但它不依赖任何人的环境变量，明天换个人维护也能跑。

第二层是**工作目录**。cron 执行任务时的工作目录，一般是执行用户的家目录；用 root 跑就是 `/`。如果脚本里写的是 `open("data/x.csv")` 这种相对路径，手动跑因为你在项目目录里，找得到；cron 跑，它站在根目录下找 `data/x.csv`，当然找不到。修法有两条：crontab 里写 `cd /data/xxx && ./run.sh`，或者干脆让脚本自己管——开头 `os.chdir` 到固定目录，或者所有路径写绝对路径。我更倾向后者：一个要长期无人值守的任务，不该假设自己站在哪儿。

第三层是**shell 不一样**。cron 用的是 `/bin/sh`，不是 bash。`set -o pipefail`、`[[ ]]`、数组，这些在 sh 里没有。表现是脚本在终端手动跑得好，定时跑就报一行莫名其妙的语法错。如果脚本必须是 bash 写的，那就 shebang 写清楚 `#!/bin/bash`，并且调度时用 `bash 脚本.sh` 显式调用，别指望它自己会切换。

第四层，也是最容易被忽略的：**输出没人接了**。在终端里跑程序，屏幕就是你的日志；cron 里没有屏幕，标准输出和错误默认会被 cron 攒起来当邮件发给你，而这台机器根本没配邮件服务——于是它们被直接丢掉。丢掉的不只是正常输出，包括错误。这就是我那次"三天没跑"的真正原因：任务其实失败了，而且第一晚就失败了，只是没有人知道。

所以给定时任务加日志不是"锦上添花"，是入场券。我的默认写法是 `>> /data/xxx/logs/run.log 2>&1`，`2>&1` 不写就等于把错误扔了。日志里还要有时间戳，标准输出本身不带时间，光看一行行文字根本不知道是哪个时间点出的问题。再加一条经验：日志要按天分文件或者定期切，不然半年后你面对的是一个几百兆、翻都翻不动的文件，等于没有日志。

第五层是**没有人看着它**。在终端里跑，卡住了你一眼就看见；在 cron 里跑，卡住了它就一直卡着，然后下一个周期到了，cron 又拉起一个同样的进程。两个进程同时往同一个文件或同一张表里写数据，结果是数据坏了、但没有任何一处报错。这种事我吃过一次，比"任务没跑"难查十倍——因为表面上看任务每天都在跑。后面我给这类任务都加了两道保险：一是用 `flock -n` 加锁，抢不到锁就直接放弃这一次，绝不并行；二是任务自己在开工时写一行开始、结束时写一行完成，第二天早上我只用检查"昨晚有没有那行完成"，不需要读全部日志。

最后一层，是**退出码和汇报**。终端里命令失败，你会看到 exit code；cron 里失败就是静默。所以我现在会给任务收一个尾：`|| echo "$(date '+%F %T') FAILED" >> /data/xxx/logs/status.log`。日志本身不产生任何动作，产生动作的是检查。成功要留一行，失败也要留一行，然后有一个更简单的任务每天去看这两行——不刷屏、不通知，只在异常时说话。

还有些小坑值得记一下。crontab 里的百分号不是字符，是特殊符号，命令里真要写 `%` 得写成 `\%`。五个时间字段的顺序是"分 时 日 月 周"，`*/10` 才是每十分钟，写成 `10` 就是每小时的第 10 分钟。还有时区：服务器如果是 UTC，你脑子里想的"早上八点"在 crontab 里是 0 点，任务会在你最不想它跑的时间点启动。写完一行 crontab，我现在的习惯是 `date` 看一眼当前时区，再 `grep CRON /var/log/syslog` 确认它确实按我理解的时间触发了。

回头看，定时任务真正难的地方从来不是那五行时间表达式，语法十分钟就能学会。难的是意识到"我在终端里跑通"这件事本身包含了一大堆隐藏前提：我的路径、我的目录、我的 shell、我盯着的屏幕。定时任务要求的，是把这些前提一条条写下来，写进脚本、写进配置。它其实是一份合同：你不写明的部分，它一律按缺省值执行——而缺省值里没有你。

**一句话：定时任务不是"换个时间跑同一个脚本"，而是"搬进一个没有你、也没有你环境的房间"，所以它必须自己带全绝对路径、带日志、带上锁、带汇报——写清楚，它才靠得住。**
