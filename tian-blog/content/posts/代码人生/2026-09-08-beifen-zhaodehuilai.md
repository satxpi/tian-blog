title: 备份不是存起来，是找得回来

这台服务器上存着我这几年写的全部文章，一堆 Markdown 文件，加起来还没有手机里一段视频大。论体积，随便一个游戏都比它大；论价值，丢了它们我写不回来。硬盘会坏，机房会出故障，账号会出问题，这类事不发生则以，发生就是全部归零，而且不会提前打招呼。数据这东西，最不值钱的时候是它还在的时候，最值钱的时候是你发现它没了的那一秒——可惜那一秒已经晚了。

这些文件每天还在长新的。早上定时任务写文章、构建、推送、上线，归档脚本再同步一份进资料库，链条看着完整，我也一直默认数据是安全的——服务器一份、GitHub 一份、归档一份，三份呢。直到上个月翻了一次车：定时任务半夜超时被系统杀掉，文章文件其实已经写好，安安静静躺在磁盘上，就差提交和推送两步，第二天我从 git log 的空白里才发现。那天我盯着这篇没推出去的文章想：要是昨晚硬盘坏了呢？它就没了。因为"推上 GitHub"这件事压根没发生，我以为存在的异地备份，只是我脑子里的想象。

那次之后我想明白一件事：备份的判断标准只有一条——这台机器明天原地消失，你的数据还在不在？在，才叫备份。不在，你在硬盘上复制多少份都没用，那只是同一份风险的多个分身。服务器上存一份、归档目录放一份，看着是两份，其实睡在同一块硬盘上，电源一断一起没。圈里有个流行的说法叫三二一原则：至少三份拷贝、两种不同介质、一份放在异地。道理是对的，但很多人只记住了"三份拷贝"，把后半句"异地"给忘了。异地两个字才是灵魂：拷贝再多，只要都在这台机器上，机器出事就是团灭。真正的备份必须离开这台机器。对写东西的人来说，最便宜的异地备份就是 git push：推上去那一刻，数据就躺进了别人的机房，跟你这台机器的生死解除了绑定。所以我现在认的死理是：文章落盘不算数，commit 也不算数，push 成功那一刻才算数。检查十遍本地文件，不如看一眼 git log 里有没有当天的提交。

想明白这条，新的坑马上又来了：备份的链条会自己悄悄断掉，而且断得无声无息。git push 偶发断连，报错是显性的，重试就行，不可怕；可怕的是假装成功的失败。公众号的草稿接口我就撞上一次：接口返回成功，media_id 都给出来了，草稿箱里却翻不到这篇——它假成功。要不是我对"系统说成功"这件事向来留个心眼，这篇稿子就当已经发出去了。CI 构建偶尔也会闷声失败，线上还挂着昨天的页面，不 curl 一下根本不知道。这些教训归结成一句话：回执不等于成功，成功要以另一端真的收到了为准。系统告诉你"成功了"，只是它完成了自己那半段，后半段通没通，得自己去确认。单看每一环都是小概率事件，但备份是一根链子，链子上每一环都可能断，断的次数一多，断链只是时间问题。所以"我做过备份"是句没意义的话，有意义的是"我的备份今天还在工作"。备份不是一次动作，是一次体检——不是做了就完事，得定期做，最好天天做。

体检靠人肉记忆靠不住，人会累、会忘、会觉得"昨天刚查过没事"。所以能交给机器的验证，我一律交给机器：定时任务跑完有没有报错，看一眼就知道；线上是不是最新版，脚本 curl 一下就知道。机器报错是显性的，看到了当天就修，绝不攒着。至于 git log 里有没有当天的提交这种一眼能看完的事，隔三差五自己过一遍，全绿才安心。这套规矩不是我拍脑袋想出来的，是翻车翻出来的：故障这东西，当场抓住是小事，攒到要用数据那天才暴露，就是事故。备份这行还有个终极考试，比日常体检更硬核——找一台跟这台服务器毫无关系的机器，把仓库从头 clone 一遍，文章一篇不少地出现在眼前，那一刻你才算真正确认备份是活的。我没事不会真等到灾难来才考这场试，但心里始终绷着这根弦：真等到硬盘报废才第一次验证备份能不能用，那不叫备份，叫赌博，赌注是几年的心血。我赌不起——写出来是运气，丢了可不会凭运气回来。

数据这东西脾气很怪：丢之前，你嫌它乱、嫌备份麻烦，觉得每天 push 多此一举；丢之后，你愿意花任何代价把它找回来，它偏偏回不来。备份花的成本，说到底就是"多看一眼"这点力气，买的却是明天还能接着写。别问一个人备份了几份，问他上一次确认备份还能用是什么时候——答得上来的，数据才是真的安全。
