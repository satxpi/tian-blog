# 日志写了三屏，出事时一句有用的都没留下

有一次线上一个任务出了问题，我打开日志文件，从头翻到尾。几百行，密密麻麻，全是这种句子：任务开始、任务结束、处理完成、共处理 0 条。

看得我心里发堵——日志最密集的那两个小时，恰恰是我最想知道发生了什么的那两个小时，它一句有用的都没说。

我想知道的是：从哪一步开始不对的？错在谁身上？影响的是全部还是一小撮？它憋着不说。那不叫日志，那叫打卡机。

后来我给自己定了一条很朴素的标准，用来判断一份日志到底写得好不好：**假如你现在手上没有任何别的线索，只能看这份日志，你能不能把那次事故还原出来。** 还原不出来，就是没写。

## 很多人写的不是日志，是进度条

进度条式的日志，最大的特点是它只对写的人有安慰作用。

"任务开始""任务结束"能说明什么？只能说明代码确实走到那一行了。至于它带了什么进去、拿到了什么出来、花了多久、有没有中途跳过——一个字都没有。出事的时候你盯着"任务开始"，唯一的感受是：我知道它开始了，然后呢？

真正有用的日志，至少得同时交代三件事：什么时候、在哪一步、结果如何。

时间要带上时区。这一点吃过亏的人都知道——机器是 UTC，你看的是本地时间，两边差八个小时，你顺着一根时间线找，怎么对都对不上，最后发现是自己看错了表。（这事我另写过一篇，不展开了。）

"在哪一步"不是指行号，而是指业务上的位置：是读数据那一步，还是写库那一步，还是调对面接口那一步。日志里写一句"第 3 阶段开始"，比打印一百行变量都管用。

"结果如何"是最容易漏的。写"处理完成"没有意义，要写"处理了 4123 条，跳过 7 条，失败 0 条，耗时 18.4 秒"。数字一出来，下次再跑同一件事，你一眼就知道是快了、慢了，还是少了。数量对不上，你甚至会主动去查——而"处理完成"这四个字，永远不会让你想起来查任何东西。

## 一条日志救不了你，能串成一条线的日志才可以

单个服务里的日志还算好办，麻烦的是它跑了出去。

一个请求进来，经过三四层，最后落到别的服务、别的机器上，日志也散在四五个文件里。这时候你要是没有一样东西把同一件事的所有日志串起来，排查就变成了考古：你拿着一串时间戳，在几个文件里来回对，靠猜。

所以请求 ID 这种东西，看着不起眼，是分水岭。每个请求进来生成一个，往后每一层、每一条日志都带上它，排查的时候一条 grep 就能捞出一整条线，像看一个故事从头到尾。没有它，并发一上来，同一秒里几百条日志混在一起，光靠时间你根本分不出哪句属于哪件事。

## ERROR 多了，等于没有 ERROR

日志级别用久了，很容易通货膨胀。

有人把"重试了一次就成功了"也打成 ERROR，有人把真正的失败打成 INFO 悄悄藏起来，还有人把 ERROR 当成提醒通道，一天往上打几百条。两三个星期以后，这份日志里最真实的一句话就是：反正每天都刷屏，没人会看。

于是真正出事的那一条，就被埋在自己人的噪音里了。

我现在用的判断标准只有一句：ERROR 意味着"某个地方需要有人动手了"。不需要动手的，降级成 WARN 或者 INFO；需要动手的，就别藏在 INFO 里等人碰巧翻到。级别不是装饰，它是给未来的自己留的一条分诊线，乱标等于把分诊台拆了。

跟这个意思相近的，是异常处理里那句偷懒的写法：只打印错误信息，不打印堆栈。日志里留一句"操作失败"，你连它是在哪一层失败、被谁调起来的都不知道，等于现场只剩下半根鞋带。堆栈再丑、再长，那也是现场。

## 日志不能当垃圾桶，也不能当数据库

往里扔东西这件事，两头都容易出事。

一头是敏感信息。密码、token、手机号、身份证、完整的请求体，很多人图省事直接打进去。你打的时候觉得"就我自己看"，可日志文件是会被轮转、被备份、被同步、被抓到某个你根本想不起来的地方去的。它不是只躺在你机器上等你，它会到处走。

另一头，是把它当数据源用。业务量靠 grep 日志统计、用户行为靠翻日志找——一开始真省事，格式一改全废，而且随着量上来，越查越慢。日志回答的是"为什么出事"，数字统计该交给正经的指标或者数据库。这两件事混在一根管道里，早晚有一头要坏。

顺一句，指标和日志的分工其实很清楚：日志告诉你为什么，指标告诉你多少、什么时候开始的。没有指标，你的第一次发现永远来自用户投诉；而靠用户投诉发现的问题，通常已经不止一次了。

## 写的时候多花三十秒

我现在写日志会做一件很傻的事：写下那一行之前，先想一下半年以后凌晨三点的自己——困得睁不开眼，手上没有别的线索，只能看这一行。

他会希望我现在多写点什么？当时的输入是什么、期望的结果是什么、实际拿到的是什么、从哪一步开始偏的。想清楚这四个问题，一条日志就自然地写出来了，而且写的时候也就多花三十秒。

这三十秒大概率是要不回来的：你会写很多很多条日志，其中绝大多数一辈子都不会有人打开第二次。可真正需要它的那天，它换回来的是三个小时、一个不用猜的结论，和一次没有惊动用户就修好的机会。

程序会自己运行，会自己报错，但它不会自己解释。日志就是你替它写下的那份解释——写的时候敷衍，出事的时候就没人替你说话。
