# 两个程序同时写一个文件，谁都没报错，数据却少了一半

去年我在一台机器上挂了个小脚本，干的事很简单：每抓到一条数据，就把一个 JSON 文件读出来，往列表里塞一条，再整个写回去。文件里本来该有当天的全部记录，一天下来几百条。跑了几天，我发现文件里的条数总比数据库里的少一点，少得不多，一天二三十条，随机分布在各个时段。

没有报错。日志干干净净。进程一直在跑，退出码是 0。

这种问题最难受的地方不是难修，是**它不承认自己有问题**。你去查，每一环看起来都对：脚本在跑，文件在长大，内容也合法，`json.load` 一次就能读出来。只有那个数字对不上。

后来我把两个进程的时间戳打出来才看明白：这台机器上有两个实例在跑同一份逻辑，一个是我手敲的，一个是 cron 拉起来的。它们几乎同时读到同一个版本的文件，各自塞进自己那条记录，各自写回去。后写的那个把先写的整个覆盖掉。**两份完整、合法的 JSON，前一份被后一份从头盖到尾，连个响都没有。**

## 覆盖是合法的，所以没人报警

我们对"出错"的直觉来自编译器和异常：语法错、类型错、文件不存在，这些都会喊。但"后写覆盖先写"在所有操作系统眼里都是一个完全正当的操作。你打开文件写入，系统就照办，它没有义务记得上一次是谁写的、写了什么。

Python 里这行代码是罪魁祸首：

```python
with open(path, "w") as f:
    json.dump(data, f)
```

`"w"` 这个模式看着温和，实际动作是两步：打开文件的那一瞬间，内核先把文件长度截成 0(`O_TRUNC`)，然后才开始写。也就是说，**从打开到写完这段时间里，磁盘上存在过一个 0 字节的文件**。如果另一个进程恰好在这几十毫秒里来读，它读到的不是"旧数据"，而是空。

这也解释了一个大家大概都见过的报错:

```
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

`char 0` 特别值得注意。它不是说文件末尾被截断了，是在说**第一个字符就不对**——因为那时候文件是空的，或者写了一半。很多人第一反应是"JSON 文件损坏了，重新生成一份"，然后过几天它又坏一次，因为损坏不是意外，是并发下的正常产物。

## 写不是一瞬间的事

"写文件"这三个字在我们脑子里是一个点，在系统里是一段过程：应用程序的缓冲区 → 内核的页缓存 → 磁盘。Python 的文本层还有自己的缓冲，一条几百字节的记录，可能被拆成好几次 `write` 系统调用发出去。

两个进程都用追加模式（`"a"`）也一样救不了。追加不覆盖，但会**交错**：A 写了半条，B 插进来一条完整的，A 再把后半条补上。打开日志看到两行记录粘在一起、或者一行被劈成两半夹在别人中间，就是这个。追加模式能保证的是"大家都往末尾放"，不保证"每次放的是完整的一坨"。

所以"我们没做删除，只是追加，应该安全"这个推断，在并发面前是站不住的。

## 两种修法，治的不是同一个病

第一种，让**写**变成原子操作。做法是：新内容写到一个临时文件，写完了、`flush` 完了，再用一次 `os.replace(tmp, path)` 把它换上去。

```python
tmp = path + ".tmp"
with open(tmp, "w") as f:
    json.dump(data, f)
    f.flush()
    os.fsync(f.fileno())
os.replace(tmp, path)
```

`os.replace` 在同一个文件系统内是一次原子重命名。它的效果是：**任何时刻来读的人，要么读到完整的旧文件，要么读到完整的新文件，不存在中间态。** 那些正在读旧文件的进程也没事，它们手里握着的是旧的 inode，会安安静静把旧内容读完，新文件跟它们无关。这个细节我特别喜欢，它说明"替换"其实不是改内容，是换了个名字指向别处。

但注意，这只解决了"读到半截"的问题，**没有解决丢更新**。两个进程照样可以都读旧版本、都写新版本，最后一个赢。原子替换让文件永远合法，不让数据永远齐全。

第二种，让**读-改-写**这一整段变成互斥。用 `fcntl.flock` 加把锁：

```python
with open(lockpath, "w") as lk:
    fcntl.flock(lk, fcntl.LOCK_EX)
    data = json.load(open(path))
    data.append(record)
    ... 写回 ...
```

这把锁得在"读之前"就拿到，读完、改完、写完了才放。要是先读后加锁，等于门口排队却先进屋逛了一圈，白排。另外 `flock` 是建议锁——不调它的进程照样能直接写，它管不了不守规矩的人，只对"都愿意排队"的程序有效。NFS 上它还经常不灵。

如果嫌麻烦，还有个更省事的答案：**别用 JSON 文件当数据库**。SQLite 自带事务和文件锁，`INSERT` 天然原子，几百条记录的量级完全够用，连服务都不用起。我们常常为了"轻量"选一个纯文本文件，然后在并发上花掉十倍的调试时间——这笔账很少算得清。

## 真正的问题是：你以为有顺序

排错排到最后，我发现根子上不是代码写得糙，是我脑子里有个默认假设：**这些事是按我想的顺序发生的**。

我写"读出来、加一条、写回去"的时候，脑子里是一条时间线，像流水线一样一格一格往前走。但机器上没有这条线。两个进程各自有自己的一条，谁先谁后由调度器决定，而调度器不认识你的业务逻辑。你写的三步，在它眼里是三次互不相干的系统调用，中间随时可以插进别人的一万次操作。

这就是并发问题为什么总在"看起来没问题"的地方爆。它不是某种罕见的边界情况，而是**系统本来就这样运行，只是平时没撞上**。数据少 2% 的时候你以为是抓取失败，少 20% 的时候你以为是磁盘坏了，等到少一半，才会开始怀疑自己的假设。

所以后来我给自己定了个很土的办法：凡是"读一个东西、改一改、写回去"的代码，先问一句——**如果这段同时跑两份，会怎样？** 想不出答案的，就先当它会有问题，加锁或者换成原子替换。这个问题问起来只要五秒钟，比事后对着两个时间戳发呆一晚上便宜太多。

那天我把脚本改成先抢锁、再原子替换，数据一条不少。文件还是那个文件，代码也没变聪明，只是我不再假设它一个人在用。
