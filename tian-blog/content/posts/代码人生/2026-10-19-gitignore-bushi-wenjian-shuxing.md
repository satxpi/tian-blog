# .gitignore 管不了已经提交的文件：忽略是一种状态，不是文件的属性

前几天整理一个跑了半年的小项目，`.git` 目录四百多兆，换台机器 clone 一次要等两分钟。我倒也没写什么大功能，主要是脚本每天跑出来的 csv 和日志，一天几兆，半年下来就这个数了。

打开 `.gitignore`，里面明明早就写了：

```
data/
*.log
```

我以为是哪次手滑没生效，索性又补了一行 `data/*.csv`，提交，推送，`git status` 干净了。第二天脚本跑完，一敲 `git status`，又满屏的 `modified: data/2026-10-19.csv`。

那一刻我才认真去看：`.gitignore` 到底在管什么。

## 它管的是"还没被跟踪"的文件

在 git 眼里，工作区里的文件只有两种身份：**已跟踪**和**未跟踪**。已跟踪的文件，git 会盯着它的大小、修改时间、内容摘要，随时准备把变化记下来；未跟踪的文件，git 只是路过看一眼，提醒你"这儿有个新东西"。

`.gitignore` 的作用只有一句话：**给那声提醒装一个过滤器**。它不改变文件，不改变权限，也不改变 git 有没有能力读它。它只是让 `git status` 和 `git add` 在看到某个路径时闭嘴。

所以它天然只对**还没被跟踪**的文件生效。某个文件只要被 `git add` 过一次，它就被登记进索引（index），从那一刻起，git 认为"这个文件的变化归我负责"。之后你在 `.gitignore` 里写什么，它都不看了。

于是会出现那个很别扭的现象：新生成的 csv 完全不出现在 `git status` 里，说明忽略规则是生效的；可**最早那个 csv** 一直显示已修改，一直可以被提交，规则对它形同虚设。

原因通常特别朴素：项目第一天，目录还空着，顺手一句 `git add .`，把当时 `data/` 里仅有的几个文件一起收进了库。`.gitignore` 是后来吃了亏才想起来的。规则写在后面，管不了前面已经发生的事。

## 要改的不是规则，是状态

正确做法不是再补一行规则，而是把那层跟踪关系解掉：

```
git rm -r --cached data/
```

`--cached` 是这句话的全部要害：只从索引里删，磁盘上的文件一个不动。用不带 `--cached` 的版本，文件会跟着被删掉——这是很多人第一次用 `git rm` 时的心跳时刻。

然后正常提交这次删除。提交信息别写"删除数据"，写清楚"停止跟踪 data 目录，改由 .gitignore 忽略"。因为这次提交删掉的是**git 对它的跟踪关系**，不是数据本身。同事拉下来，他们本地的文件也还在，只是 git 不再管了。

改完状态，`.gitignore` 才开始起作用。

## 但仓库并没有因此变小

这是第二个容易失望的地方。索引里删掉只影响以后，**历史里那些 blob 一个都没少**。之前每一次提交都还引用着它们的旧版本，那些字节永远躺在 `.git/objects` 里，直到被真正清理。

想让仓库瘦下来，得重写历史，比如 `git filter-repo --path data/ --invert-paths`。这是另一件工程，代价是所有提交的哈希都会变，所有同事必须重新 clone。所以我后来学乖了：**数据目录从第一天就该在忽略名单里**，而不是等它胖到四百兆再想办法。

## 三种"我明明写了却不生效"

写忽略规则最常遇到的困惑，其实不是删不掉，而是写了没反应。我踩过的几处：

**路径的写法有讲究。** `data/` 匹配任意层级的 `data` 目录；`/data/` 只匹配仓库根目录下那一个；`data` 不带斜杠，则文件和目录都会匹配。差一个斜杠，命中的范围完全不同。

**规则是按顺序覆盖的。** 后写的规则压前面的，所以"先全部忽略，再单独放行"要这么写：

```
*.log
!important.log
```

反过来写就没用。另外规则有层级：同目录的 `.gitignore` 优先于上级目录的，`.git/info/exclude` 排在后面，全局配置里的 `core.excludesFile` 排最后。近的那份赢。

**文件已经进库了。** 就是前面说的那件事，规则再对也没用。

排查不用猜，git 自己给了工具：

```
git check-ignore -v data/2026-10-19.csv
```

它会打出命中的是哪一行、来自哪个文件的哪条规则。如果什么都不输出，那答案就很清楚了：没有任何规则匹配到它，它多半已经在索引里了。

顺便说一句，`.gitignore` 本身是要提交的——它是项目的约定，不是你的私人习惯。真正属于"我个人的事"的，是 `.git/info/exclude`，放编辑器缓存、临时笔记正合适；再往上一层，`~/.gitconfig` 里指向的那个全局忽略文件，适合放 `.DS_Store`、`Thumbs.db` 这类走哪都碍眼的东西。

## 比仓库变胖更贵的，是密钥

我后来对这件事真正上心，不是因为体积，是因为一次差点出事的配置。

有个小工具的配置文件里直接写了数据库密码，第一版提交时就跟着进去了。第二天我想起来，赶紧把它加进 `.gitignore`——加完心里还松了口气，觉得自己处理得挺及时。

其实那时候什么都没处理。加进忽略名单只意味着"以后不提醒我"，不意味着"以前没发生"。那把密码还完整地躺在那次提交里，任何人 clone 下来，一句 `git log -p` 就能看见。

所以顺序不能反：**先作废那把密钥**——改密码、吊销 token、重新生成；**再清历史**。清历史是卫生工作，不是安全措施。历史重写之后，别人手上的旧 clone、fork、CI 缓存里，旧提交还在。

## 说到底

`.gitignore` 不是文件的属性，它更像我给 git 的一句话：**这个还没进你视野的东西，别提醒我**。它说的是"动作"，不是"归属"。

文件一旦进了索引，就跟规则脱钩了。真想让它不管，得先解掉跟踪关系，而不是在规则文件里再写一行——那行字写多少遍，都不会生效。
