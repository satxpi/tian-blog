# 返回 0 不叫成功，叫"我没崩"

一个备份脚本跑了三十一天，cron 每天凌晨三点执行，日志干净得像刚洗过，从来没有哪一封报错邮件。第三十二天我要恢复一个文件，打开备份目录，里面是一个 `backup-2026-11-23.tar.gz`，大小 20 字节——gzip 的空壳。

回看脚本，逻辑简单到不该出事：

```bash
tar cf - /data/share | gzip > /backup/backup-$(date +%F).tar.gz
echo "备份完成 $(date)"
```

第一条命令的 `tar` 其实一直在报 `file changed as we read it`，返回码 1。但整条管道的返回码取的是最后一个命令，也就是 `gzip` 的 0；紧接着那句 `echo` 又把整个脚本的返回码刷成了 0。于是 cron 看到 0，判定成功，安静地走了三十一天。

这件事让我把"退出码"这个东西重新想了一遍：**退出码不是"事情办成了"，是"程序自己认为它结束了"。这是两件完全不同的事，中间隔着整个世界。**

## 0 到 255，一个字节的遗言

进程结束只有一条主路：调用 `exit_group(status)`。这个 `status` 是个 int，但内核往父进程那边只传低 8 位。所以退出码永远是 0 到 255，255 个可能值（0 算成功）。

这解释了一批看起来像 bug 的现象。C 里写 `return -1`，shell 里 `$?` 拿到的是 255。写 `exit 256`，拿到的是 0——一个失败被截断成了成功。写 `exit 1000`，拿到的是 232。想靠"用大数字表示某一类错误"来传递信息的人，最后都会撞到这堵墙上。

约定是这样的：0 表示成功，非 0 表示失败。但这份约定比它的字面意思弱得多。它没有规定失败要怎么分类，没有规定 1 和 2 和 3 分别是什么，也没有任何内核强制。整件事完全靠程序自觉——**退出码是程序对自己的评价，不是对现实的描述。**

`grep` 是个好例子。找到返回 0，没找到返回 1，文件打不开返回 2。注意那个 1：它不是"出错了"，它是"我问的问题的答案是否"。但如果你在 `set -e` 的脚本里写一行 `grep -q pattern file`，没匹配到，脚本当场静默退出，后面的清理逻辑一个都不跑。语义错位就是这么来的：**一个程序眼里的"正常的否定回答"，在另一个程序眼里就是"出事了"。**

`rsync` 更绝。它有 24 个退出码，其中 24 是 `some files vanished during transfer`——源文件在传输过程中被删了。这既不算成功也不算失败，但脚本里 `rsync ... || echo 备份失败` 会把它当失败，然后在完全正常的一次备份之后给你发一封警报。发多了人就麻木了，麻木之后就真的漏事了。

## shell 把退出码弄丢的十种方式

管道那个坑最深，因为它长得最合理。`a | b` 的退出码是 `b` 的。这意味着 `a` 死了你都不知道。

```bash
tar cf - /data | gzip > out.gz     # tar 失败，退出码 0
cat big.log | head -3              # cat 被 SIGPIPE 打死，退出码 0
mysql < dump.sql | tee log         # mysql 报错，退出码是 tee 的
```

第二种尤其阴险：`head` 读够三行就关了读端，`cat` 再写就吃 `SIGPIPE` 直接死。它其实是"被杀"的，但在管道里它连"死"都排不上——退出码由 `head` 决定。

解决办法是 `set -o pipefail`：管道里任何一个命令非 0，整条管道就是非 0。配一句 `set -euo pipefail` 几乎是现代 shell 脚本的标准开头。但要注意 `pipefail` 是 bash/zsh/ksh 的东西，POSIX 的 `sh`（很多发行版上是 `dash`）没有这一项，写了会报 `set: Illegal option -o pipefail`，然后脚本直接退出——为了更安全而让脚本更早死，也算一种讽刺。想查得更细，bash 有 `PIPESTATUS` 数组，管道里每个位置的真实返回码都在里面。

`set -e` 本身也有好几个洞。它不生效的场合包括：命令出现在 `if`/`while`/`until` 的条件里；出现在 `&&`、`||` 的左边；被 `!` 取了反；出现在管道里非末尾的位置（不开 `pipefail` 时）；以及函数体被调用时若函数本身处在这些上下文中，里面全部失效。

还有一个纯粹恶心人的：`((i++))`。当 `i` 是 0，这个算术表达式的值就是 0，算术命令把"值为 0"当成失败，于是 `set -e` 下脚本退出。整段循环一次都没跑就结束了，日志里什么也没有。要写成 `((++i))` 或者 `((i++)) || true`，或者干脆用 `i=$((i+1))`。

最后是那个最普遍的：**脚本的退出码等于最后一条命令的退出码**。所以任何在结尾加一句 `echo "任务完成"` 的脚本，都在结构上放弃报告失败。更隐蔽的是结尾的 `rm -f tmp/xxx`、`cd`、`[ -d log ]`——它们会把前面的所有错误一笔勾销。想保险，就在关键步骤后面显式判断，结尾显式 `exit 0`，别让一条无关的命令替你做结论。

## 137 不是错误，是被人从背后捅了一刀

上面的都是逻辑问题，还有一整类退出码讲的是另一件事：进程被信号杀了。

shell 里看到的数是 128 加信号号：`SIGKILL`（9）→ 137，`SIGTERM`（15）→ 143，`SIGSEGV`（11）→ 139，`SIGINT`（2）→ 130。所以 Docker 容器里看到一个 137，标准解释是"内存超限被内核 OOM killer 干掉了"，或者"被人 `docker stop` 超时后强杀"。它不代表你的代码有逻辑错误，它代表有人（内核也算人）替你按了停止键。

这里有个容易踩的差异：shell 把信号折成 128+n，Python 的 `subprocess` 模块返回的是负数，`-9` 就是 `SIGKILL`。同一件事，两个数字体系。写告警规则的时候如果按 137 去匹配，Python 那边永远匹配不上，然后你会得出"没有发生过 OOM"这个结论。

顺带说，`SIGTERM` 能不能被接住决定了退出码好不好看。程序不捕获 `SIGTERM` 就直接死，退出码 143；捕获了、清理完、`exit 0`，退出码就是 0。所以同一个容器，有时 `docker stop` 后退出码是 0，有时是 143——差别只在代码里有没有那个 `signal.signal` 或者 `context.WithCancel`。**"退出码 0"在这里什么都不证明，它只证明进程死得体面。**

## 真正的判据是产物，不是遗言

`curl` 是最好的反例。它默认只关心"HTTP 请求有没有完成"，服务器返回 500、404、403，只要 TCP 连通、报文走完，退出码就是 0。你写

```bash
curl -s https://api.example.com/health > /dev/null || echo "服务挂了"
```

这一行永远不会报错，哪怕对面整个数据库都烧了。要么加 `-f`（`--fail`，4xx/5xx 时返回 22），要么显式检查状态码：

```bash
code=$(curl -s -o /tmp/h.json -w '%{http_code}' https://api.example.com/health)
[ "$code" = "200" ] || exit 1
```

脚本、SDK、命令行工具，凡是"操作成功"和"业务成功"分开的东西，都有这个缝隙。数据库连上了、SQL 执行了、影响 0 行——退出码 0。文件写进去了、内容是空的——退出码 0。API 通了、返回 `{"ok": false}`——退出码 0。

所以判断一次任务到底成没成，唯一可靠的办法是回到产物本身，并且把"成功的定义"写成代码：备份要看文件大小和 `tar tzf` 能不能列出来、条数对不对；同步要比两边的计数；导出要检查行数和关键字段非空；发文章要 `curl` 一次线上地址确认 200 并且正文里有那一段。这些东西写起来麻烦，但它们是唯一说真话的部分。

```bash
set -euo pipefail
tar czf "$DST" /data/share
tar tzf "$DST" > /dev/null          # 能列出内容才算包完好
[ "$(stat -c%s "$DST")" -gt 1000000 ] || { echo "包太小，可疑" >&2; exit 1; }
```

四行，比原来那两行多一行校验、多一行显式失败，就能把一个连续三十一天撒谎的脚本按住。

回到那个 20 字节的包。它的退出码是 0，它的 tar 文件头是合法的，它甚至能用 `tar tzf` 列出一个空目录——只有大小暴露了它。三十一天的沉默不是因为哪个环节坏了，是因为所有环节都"正常结束"了，而没有一个人去问一句"你办成了吗"。

**退出码是程序对自己说的话，不是对事实的描述。想要知道事情办成没有，只能去检查产出来的那个东西。**
