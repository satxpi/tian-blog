# too many open files 不是文件太多：一个进程只有 1024 个号码牌

服务跑了三天，日志里开始出现这一行：

```
OSError: [Errno 24] Too many open files
```

重启，好了。再过三天，同样的一行又来了。

第一反应是去数文件：`ls | wc -l`，那个目录里三百多个文件；`df -i`，inode 用了不到百分之十。磁盘空着，文件不多，系统好好的，那到底是谁"太多"了？

答案在报错的主语上。这句报错的主语从来不是"文件"，是**这个进程手里同时握着的句柄数量，超过了它自己的配额**。文件多不多，跟它没关系。

## 号码牌不是文件，是一个进程的私房账

Linux 里"一切皆文件"，这句话在性能优化文章里被引用得太随意，真正的后果在这里：进程访问任何东西，都要先跟内核要一个整数，叫文件描述符（fd）。普通文件要，socket 要，管道要，`epoll` 实例要，`eventfd` 要，`/dev/urandom` 也要。

这个整数是进程私有的，从 0 开始编号：0 是标准输入，1 是标准输出，2 是标准错误。往后每开一个东西，就往后发一个号。号本身没有意义，它只是"进程自己那张表"的下标，表项指向内核里的真实对象。

所以同一份文件被两个进程打开，会拿到两个互不相干的 fd；反过来，一个进程里两个 fd 完全可能指向同一个文件。**fd 是打开的次数，不是文件的个数。**

默认配额是多少？`ulimit -n` 敲下去，多数系统回你 `1024`。这个 1024 不是随便定的，它来自 `select()` 那个老接口的 `FD_SETSIZE`，一个用了三十年的历史包袱。今天没人用 `select` 了，但这个默认值还活在无数台服务器上。

一个进程 1024 个号。听着很多，可一个服务里，每个进来的 TCP 连接占一个，每个连出去的下游连接占一个，连接池预建 50 个，日志开 3 个，临时文件一开一关再一开——几百个号转眼就没了。跑到第 1025 个，内核回你 `EMFILE`。

顺带说清一对容易被混为一谈的错误：`EMFILE` 是**进程级**配额用光，`ENFILE` 是**系统级**配额用光（`/proc/sys/fs/file-max`）。前者提高 ulimit 就能解决，后者是你把整台机器的名额都吃完了，别的进程跟着遭殃。报错文本一模一样，处理方式完全不同。

## 谁在吃这些号

线上真正吃掉配额的东西，按我踩过的顺序排：

**一，连接。** 最正常也最大的一户。一条 TCP 连接在两端各占一个 fd，`accept()` 返回的是新 fd，监听的那个 fd 另算。所以"支持一万并发"的服务，光连接就要一万多个号，1024 的默认值连零头都不够。

**二，短连接没关。** 这是泄漏的经典形态。代码里 `socket` 建了、请求发了、异常一抛，`close()` 那行就永远走不到。表现出来是 `CLOSE_WAIT` 堆积：

```
$ ss -tan state close-wait | wc -l
2143
```

`CLOSE_WAIT` 是对方已经关了、本地还没关。这个状态在应用侧，不在内核侧，只能靠代码修。看到它成百上千地涨，八成是缺了 `finally` 或者 `defer`。

**三，日志轮转后没重开。** `logrotate` 用 `create` 模式，把 `app.log` 改名成 `app.log.1`，再建一个新的 `app.log`，可进程手里那个 fd 还指着旧 inode。它继续往"已经改名的文件"里写，`ls` 看新文件一直是空的，磁盘空间也不释放。这种 bug 特别阴，因为日志看起来"停了"，进程本身一点事没有。

**四，子进程的管道没关。** `subprocess.Popen` 开了 `stdout=PIPE`，父进程只 `read()` 不 `close()`，也不 `wait()`，三个管道对象就一直挂着。

这里顺便拆一个特别流行的误解：**大量 `TIME_WAIT` 不占 fd。** 那个连接已经被进程关掉了，只剩内核里一个状态残留，靠 `tcp_tw_reuse` 之类参数或者连接池处理，跟 `ulimit -n` 一点关系都没有。有人一看 `ss` 里几万个 `TIME_WAIT` 就去调 `nofile`，调完毫无变化，然后怀疑人生。方向从一开始就错了：`TIME_WAIT` 是内核记账，`CLOSE_WAIT` 才是你的账。

## 先数，再猜

排查我固定三步，一分钟内能定性：

```
$ ls /proc/14873/fd | wc -l
938
$ cat /proc/14873/limits | grep -i 'open files'
Max open files            1024                 1048576              files
$ ls -l /proc/14873/fd 2>/dev/null | awk '{print $NF}' | sed 's/[0-9]\+$//' | sort | uniq -c | sort -rn | head
    612 socket
    184 /data/logs/app.log
     97 pipe
```

第一行是现在握了几个号，第二行是软限制和硬限制，第三行是这些号分别指向什么。`socket` 六百多、`app.log` 一百八十多——一个日志文件被打开一百八十次，那不是并发高，那是代码在循环里反复 `open` 没关，泄漏点直接暴露。`lsof -p 14873` 能看到同样的东西，只是更慢。

软硬限制的区别也值得记一下：软限制是当前生效的天花板，硬限制是软限制能抬到的最高处。普通用户可以自己把软限制往上调，但调不过硬限制；只有 root 能改硬限制。

## 改配额为什么经常不生效

`ulimit -n 65535` 在终端里敲完，`ulimit -n` 确实变成 65535 了，可服务重启后照样报错。原因是 `ulimit` 改的是**当前 shell 及其子进程**，而你的服务不是从这个 shell 起来的。

systemd 托管的服务，得改 unit：

```ini
[Service]
LimitNOFILE=65535
```

然后 `systemctl daemon-reload` 再重启。少这一步 reload，改的文件不生效，重启一百次也没用——这种"改了配置没反应"的坑，我在 `daemon-reload` 上栽过不止一回。

容器里又是另一套：`docker run --ulimit nofile=65535:65535`，或者 compose 里的 `ulimits`；k8s 没有直接字段，得靠容器运行时的默认值或者 init 容器去写。**在哪一层起的进程，就在哪一层设限额**，这是唯一可靠的原则。

## 配额是止血，不是治病

这里是我最想说的一句：**把 1024 改成 65535，只是把复发时间从三天推到三个月。**

泄漏的代码一个号都没少要，它只是有了更大的池子可以挥霍。真正该做的是画一条曲线：每分钟采一次 `/proc/PID/fd` 的数量。正常服务在流量平稳时会走平，有轻微波动；一条持续向上、永不回落的斜线，就是泄漏，斜率除以每秒请求数，还能估出"每次请求漏几个号"。

有了这条曲线，定位基本是体力活：把请求按接口分组，看哪个接口的调用量和 fd 增长同步。我见过一个最离谱的，每次请求漏一个 fd，三天攒到一万多，重启一次顶三天，运维同事把它写进了值班手册，当成"正常现象"。那不是正常现象，那是一个每天准点开闸的水龙头，只是没人愿意去拧。

1024 这个数字本身没什么神圣的。它是三十年前一个接口的边界条件，被当成默认值继承到今天。你的服务需要多少号，取决于它同时握着多少连接和文件，不取决于这个数字。**配额应该按需要算出来，而不是被默认值推着走。**

最后回到那句报错。`Too many open files` 说的是一个进程手里的号码牌发完了，跟磁盘上躺了多少文件毫无关系。收银台前排的队再长，也不是因为仓库里的货多——是有人拿了号不还。
