# df 说磁盘满了，du 说没满：空间去哪了

上周有一台机器报警，根分区 100%。登上去看：

```
$ df -h /
Filesystem      Size  Used Avail Use% Mounted on
/dev/vda1        50G   50G     0 100% /
```

50G 全用完了。我按老习惯从根目录一层层往下量：

```
$ du -sh /* 2>/dev/null | sort -h
...
1.2G    /usr
2.8G    /var
11G     /data
```

加起来十七八个 G。剩下三十多个 G，谁也没看见。

这不是玄学。这是文件系统里最基本的一条规则被忽略了：**文件占的空间挂在 inode 上，不挂在文件名上。** 名字只是通向 inode 的一条路，路可以拆，房子不一定拆。

## 删了，但没释放

`rm` 这个命令的准确含义不是"删除文件"，是"删掉目录里指向这个 inode 的那一项"。真正决定这块空间能不能还回去的，是 inode 里记的**引用计数**（link count）和**打开计数**（open count）。两个都归零，空间才释放。

任何一个进程还拿着这个文件的句柄，计数就不为零。于是出现最经典的一幕：日志文件被 `rm` 了，nginx 还在往里写，磁盘照满不误。

```
$ lsof +L1
COMMAND   PID   USER   FD   TYPE DEVICE  SIZE/OFF NLINK   NODE NAME
nginx    1841   root    3w   REG  253,1 28.4G     0  524301 /var/log/nginx/access.log (deleted)
```

`NLINK 0`、文件名后面标着 `(deleted)`、大小 28.4G——就是它。`du` 看不见它，因为目录里已经没有这个条目了；`df` 能看见，因为 inode 还在，块还占着。

那天的情况就是这样：有人在手动清日志时用了 `rm`，而 nginx 的工作进程从头到尾没重启过，一直抱着 old inode 在写。`du` 数的是"目录树里还能找到的东西"，`df` 数的是"文件系统里实际被占用的块"，两者本来就不是同一个口径。

处理方式有两种，看你在不在意那些还没落盘的内容：

- 重启（或 reload 不够，得真正重启）写这个文件的进程，句柄一关，空间立刻回来。数据没了，但本来就是打算删的。
- 不想重启，就 `truncate -s 0 /proc/1841/fd/3`，把句柄指向的文件长度清成零，空间马上释放，进程继续写同一个 inode。这是线上最常用的救火手段。

顺便说一句，`> /proc/1841/fd/3` 和 `truncate -s 0` 效果差不多，但前者在有些 shell 配置下会写进一个空字节，还是用 `truncate` 干净。

## 正确清日志的姿势

问题的根子不在 `rm`，在于"清日志"和"日志还在被写"这两件事同时发生。日志轮转工具早就考虑过：

- `logrotate` 默认是 rename 旧文件、让写日志的进程收到信号重开（`create` 模式）。nginx、rsyslog 都支持 `USR1` 信号重开日志。
- 遇到不听话、不会重开文件的程序，用 `copytruncate`：先复制一份，再把原文件截断为零。空间能还回去，代价是复制那一瞬间写入的几行可能丢。

坏习惯是直接在 crontab 里写 `rm -f /var/log/xxx.log`。文件没了，进程还写着，空间没少，人还以为清干净了。这类脚本平时看不出问题，等磁盘满了再查，`du` 怎么都对不上账，就特别费时间。

## 还有几种"看得见摸不着"

同一个现象，还有别的成因，值得一起记住：

**一，被挂载点盖住的目录。** 往 `/data` 里写过东西，后来又把一块盘挂到 `/data` 上，原来的文件就被压在挂载点下面，`du /data` 看不见，块还占着。解决办法是 `mount --bind / /mnt/root` 之类把根挂到别处去看，或者 `umount` 之后再看。

**二，文件系统的预留块。** ext4 默认留 5% 给 root，防止普通用户把盘写满之后系统起不来。所以非 root 用户看到的 `Avail` 会比 `Size - Used` 小一截。50G 的盘，这就是 2.5G。`tune2fs -m 1 /dev/vda1` 可以调小，但对系统盘我不建议动。

**三，`df` 和 `du` 的单位不是一套。** `df -h` 的 `-h` 是 1024 进制（GiB），有些工具、有些厂商面板按 1000 进制算（GB）。50G 的盘按两种口径能差出 3.6G。看数字对不上，先确认单位，别急着找玄学。

**四，稀疏文件和空洞。** 数据库、虚拟机镜像常常是"声明了 20G，实际只写了 2G"。`du` 报 2G（实际块数），`ls -l` 报 20G（逻辑长度），两个数都对。

**五，inode 用完。** 这个更阴。`df -h` 还有空间，但新建文件报 `No space left on device`。因为 inode 耗尽了。大量小文件——session 文件、缓存碎片、几百万个空目录——能把 inode 吃干。查法就一条：

```
$ df -i /
Filesystem      Inodes  IUsed   IFree IUse% Mounted on
/dev/vda1      3276800 3276800      0  100% /
```

`IUse% 100%`，空间还剩一半也没用。这种盘只能靠删小文件救，或者当初格式化时把 `-i` 参数设大一点（代价是同样容量下能存的文件数变了，得算）。

## 我现在查磁盘的顺序

遇到"磁盘满了"这四个字，我不再一上来就 `du`。顺序换成这样：

1. `df -h` 和 `df -i` 一起看，先分清是块满了还是 inode 满了。
2. `lsof +L1 | head -30`，看有没有 deleted 还开着的大家伙。这一步最常出结果，也最快。
3. 都正常，再 `du -x -h --max-depth=1 /` 自上而下找。`-x` 别漏，不然它会跨文件系统跑进别的挂载点，越查越乱。
4. 还找不到，才怀疑挂载点遮盖、预留块、单位口径这些。

多出来第 2 步，就是这次三十多个 G 失踪教我的。`du` 是个诚实的工具，它只回答"目录树里有什么"；我拿它去回答"磁盘被谁占了"，问错了问题。

**删除不等于释放，文件名不等于文件。** 这句话听着像绕口令，但线上那次 100% 的报警，起因就是有人把这两件事当成了一件事。空间不会凭空消失，它只是还挂在某个还活着的进程手里，等着你把它找出来。
