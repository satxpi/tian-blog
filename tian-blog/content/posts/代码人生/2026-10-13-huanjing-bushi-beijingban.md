# pip 装好了包，python 却说没有：环境和代码是同一个程序的两半

前几天在服务器上装一个库，敲完 `pip install xxx`，回显一串成功，`Successfully installed`。我信心满满地敲下 `python3 -c "import xxx"`，屏幕回我三个字：ModuleNotFoundError。

装成功了，找不到。这两句话同时成立，本身就是个提示：**装包的，和跑代码的，可能根本不是我以为的同一个东西。**

我花了几分钟才把这事捋直，捋完发现，它不是一次意外，它是我见过最多的那类"程序没变、环境变了"的事故的小小缩影。

## 装包的入口和跑代码的入口是分开的

我一直以为 `pip` 是 `python` 的附属品，像一只手长在胳膊上。实际上它更像我客厅里那把备用钥匙——它开的是某一把锁，但那把锁不一定是现在这扇门上的。

Linux 上 `python3`、`pip`、`pip3` 都是独立的可执行文件，各自躺在 PATH 里的某个目录。你敲 `python3`，shell 从 PATH 的第一个目录开始找，找到哪个是哪个；敲 `pip` 也一样。它们俩谁都没义务记住对方。我这次就是——`python3` 指向 3.11，而 `pip` 这个命令背后站着的是 3.12。pip 老老实实把包装进了 3.12 的 site-packages，python3 3.11 启动后翻自己的目录，翻不到，于是报了个"我没有这个库"。

它没骗人。是我把两把钥匙当成了一把。

想确认其实很简单，一行就够：`python3 -c "import sys; print(sys.executable)"`，再 `pip -V` 看看它服务的解释器路径。两个路径对不上，那这两条命令就是两个世界的人。

## 系统的 python 不是给你装东西用的

顺着这条线往下，还有个更硬的门槛，Ubuntu、Debian 近几年的系统上都会撞上。你想给系统自带的 `python3` 装个包，它会直接拦你，扔出一句 `error: externally-managed-environment`。

第一次见挺来气，感觉系统管得也太宽了。但它拦得有道理。系统 python 是操作系统的一部分，里面的包 `apt` 要管：你手动 `pip install` 覆盖掉的那个库，等哪天系统升级，`apt` 会拿它自己那份盖回去，或者干脆因为文件冲突把升级卡死。你小心翼翼地维护的那一套版本，一夜之间就被看不见的手抹平了。

系统 python 是给你跑系统脚本用的，不是给你搭工作台的。这话说开了就一句话：**不要往你不该动的地方装东西，哪怕它当时允许你装。**

## 正确做法是隔离，但隔离也有个坑

标准答案是虚拟环境。`python3 -m venv .venv`，一个项目一个环境，各装各的，互不打架，也不会污染系统。这套东西我用了很多年，确实省心。

但它有个副作用，比想象中麻烦：**它把"环境"变成了一个需要"激活"才能生效的隐式状态。**

`source .venv/bin/activate` 之后，PATH 被临时改写，`python` 和 `pip` 才都指向虚拟环境里那一套。问题在于，这个激活状态不写在任何文件里，它只活在你当前这个 shell 会话里。换一个终端窗口、SSH 断了重连、定时任务起来、IDE 里点了个运行按钮——都可能是没激活的裸环境。于是就有了那种最让人精神分裂的现象：在你手里跑得好好的东西，交给别人就跑不起来；你昨天跑得好的东西，今天一个新终端里就崩了。

后来我学乖了一点：与其依赖"激活"这个动作，不如在脚本里直接写清楚用哪个解释器。把 `python xxx.py` 换成 `.venv/bin/python xxx.py`，路径写死，激活与否都不影响。少了那份隐式状态，就少了半夜爬起来怀疑人生的机会。

## 环境变量是没写在代码里的那部分代码

再往深一层，环境里真正会咬人的，往往是那些一个字符都看不见的东西：环境变量。

机器的 PATH 顺序决定了到底调用哪个 python，这是第一步就埋下的分歧。再往上，`LANG`、`LC_ALL` 关系着程序怎么处理文本；`TZ` 决定时间怎么算；有没有 `PROXY` 决定那句请求能不能出去；`PYTHONPATH` 会在你完全没意识到的地方，把你 import 的东西悄悄换成另一个。这些东西一个都不出现在函数签名里，也没人 review，可它们每一个都能改变程序的行为。

我们的习惯是把代码当成程序的全部，环境当成它身后的布景。可布景会换，代码不会——一出戏于是就有了两个版本。

## 交付代码，其实是交付代码加环境

想明白这层之后，我现在把话说得比较直：**一个程序的行为，等于代码加上它的环境。你只交出代码，等于只交出了一半。**

所以真正能复现的交付，都得把环境一起说清楚，而且是写在文件里、能被人读也能被机器执行的那种，不能靠口头交代"你记得用 3.11 啊"。依赖清单要锁版本，不能只写个 `requests`，得写 `requests==2.31.0`——不然今天和三个月后装出来的就不是同一个东西。跑起来的命令要写进 README 或者脚本里，别只存在你脑子里。再稳一点，干脆把整个环境打包成一个镜像，代码和它的世界一起封起来，谁来跑都是那一版。

这话听着像是我给自己的工程习惯立规矩，其实是那段报错教我的。ModuleNotFoundError 只给了我一行提示，它背后站着的是一整套没被说出口的假设：我以为装包的和跑代码的是同一个，我以为系统 python 是我的，我以为激活过一次就永远有效，我以为环境是背景。

一处都没说出口，一处都靠不住。

程序从来没骗过人，它只是把你的假设照单全收，然后在某个不经意的时刻，把那句"我以为"变成一句"找不到"。

*个人观点，请多包涵。*
