晚上整理博客仓库，随手拉了一下提交记录，从最新一条往回翻：昨天的灵岩寺、前天的休息不是停下来、再往前是苏轼、人月神话、老火车站……七十五个提交，一路滑到底，这个博客从建站到今天的完整时间线就摊在眼前。哪一天写了什么、哪一天断更了、哪一天删了一批旧文章准备重写，清清楚楚。我的 git log，就是这本博客的编年史，而我从来没刻意维护过它——只是每天提交的时候，把文章标题写进了提交信息里而已。

这件事让我重新想了想提交信息这个东西。大多数程序员把提交信息当成给机器看的说明，随便敲两个词就完事。"update"、"fix"、"modify"，甚至干脆留空。代码写完了，功能上线了，提交信息是什么无所谓，反正代码自己能说话。但代码真的能自己说话吗？能，但只说"是什么"，不说"为什么"。半年后你翻开一个文件，看到一段看不懂的逻辑，代码只会告诉你它做了什么事，不会告诉你它当初为什么存在、为什么写成这个样子、为什么绕了这么大一个弯。而这些问题的答案，只存在于一个地方：git log 里那行提交信息。

我自己就吃过亏。早年间写代码，提交信息一律是"更新"两个字，有时候连更新都懒得写，直接 -m "fix"。后来有个功能出了问题，我顺着 git blame 一路查回去，想找当初改这段逻辑的那次提交，结果看到的是一排"update"和"fix"，根本分不清哪次是哪次。没法子，只能把那一整个月的提交挨个 diff 翻出来看，花了一下午，才在某个"update"里找到了那行改动。那一刻我就明白了：提交信息不是写给 git 看的，是写给三个月后的自己看的。你写代码的时候脑子里装着全部上下文，觉得一切理所当然；三个月后，你脑子里的上下文清空了，能依靠的只有代码和那行提交信息。信息写少了，未来那个自己就要拿时间去填。

后来我慢慢养成了一个习惯：提交信息里写清楚两件事，改了什么，以及为什么改。改了什么是一句话的事，比如"修复价格精度导致的对账不平"；为什么改是更重要的那句，比如"行情源返回的浮点数有精度损失，统一改成整数分存储"。代码本身能告诉你它怎么算的，但只有提交信息能告诉你，当初是为了躲开那个坑才这么绕。别小看这句话，它相当于给未来的排查者留了一张地图。GitHub 上那些老练的开源项目，提交信息都是一段完整的小作文，标题一句话概括，正文写背景、写方案、写取舍。那不是形式主义，那是项目最廉价也最持久的文档——注释会过时，文档会跟代码脱节，wiki 会没人维护，唯独 git log 永远跟着代码走，一分一秒都不会撒谎。

提交信息还有个容易被忽略的用途：它是项目的仪表盘。git log 一拉，一眼就能看出这个项目的健康状况。提交信息写得规整、节奏稳定，说明维护者思路清楚、状态在线；提交信息全是"fix"和"wip"，说明项目长期处于赶工状态，代码多半也是乱的。这不是玄学，提交信息是工作状态的投影。我自己判断一个开源项目值不值得用，除了看 star 数，一定会翻它的提交记录：最近半年还在不在更新，提交信息写不写人话，bug 修复是打补丁还是连根拔——这些信息比 README 里吹的牛可靠得多。

说回这个博客。我每天提交的时候写的都是"每日文章: 日期 标题"，格式固定，内容就是当天文章的标题。当初这么写纯粹是为了方便——哪天文章没发出去，翻提交记录就能对上号。没想到半年下来，这行字意外成了整个博客的目录和年表：想找某天写了什么，git log 里 grep 一下日期就行；想看看自己断更过几次、什么原因断的，翻提交间隔就能还原。我从来没花过一分钟专门维护什么写作日历，git log 替我记了。

所以我现在写提交信息，心里默认的读者不是编译器，不是代码审查的人，是三个月后甚至三年后的自己，以及任何一个接手这个仓库的陌生人。多敲十几个字，成本几乎为零；省下来的，是未来某个人（很可能就是自己）对着满屏"update"发呆的一个下午。写代码是给机器下指令，写提交信息是给人留话。前者让你今天下班，后者让你半年后还能读懂自己。
