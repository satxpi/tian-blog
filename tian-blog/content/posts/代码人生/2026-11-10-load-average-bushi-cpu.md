# load average 不是 CPU 使用率：那 20 的负载从哪来

一台 8 核的机器，`uptime` 报出来是这样：

```
$ uptime
 10:42:07 up 41 days,  3:19,  2 users,  load average: 21.63, 19.80, 15.04
```

负载 21.6，按"8 核就看 8"的老经验，这台机器早该卡死了。可我同时看 CPU：

```
$ top -bn1 | head -5
%Cpu(s):  9.3 us,  1.1 sy,  0.0 ni, 78.4 id, 11.0 wa,  0.0 hi,  0.2 si,  0.0 st
```

CPU 空闲 78%，iowait 11%。业务接口响应正常，用户没投诉，监控也没爆红。

这两组数字放在一起，很多人第一反应是"监控不准"。准得很。是我一直把负载当成 CPU 使用率在看，这两件事根本不是一个东西。

## 负载数的是"想跑但跑不动的进程"

`load average` 的原始定义很简单：**在采样瞬间，处于可运行状态（runnable）和不可中断睡眠状态（uninterruptible sleep）的进程数，做指数衰减平均。** 后面那个 1 分钟、5 分钟、15 分钟，就是三个不同时间常数的平均值，越往后越迟钝。

注意它统计的单位是"进程/线程个数"，不是百分比。所以 8 核机器负载 8 意味着"平均有 8 个任务在抢 8 个核"，刚好跑满；负载 21 意味着平均有 21 个任务想跑或者卡在那儿，只有 8 个核能接。这是排队长度，不是转速。

而 CPU 使用率是"这一秒 CPU 有多少时间在干活"。一个进程卡在 IO 上等磁盘，CPU 一点没花，但它在不可中断睡眠（`D` 状态）里，照样被算进负载。这就是分母错位的地方：**CPU 使用率看你有多忙，负载看有多少人在排队。**

翻回那台机器，答案就在 `ps` 里：

```
$ ps -eo state,pid,comm | awk '$1=="D"' | head
D     2041  mysqld
D     2042  mysqld
D     1820  jbd2/vda1-8
...
```

十几个 `D` 状态的进程，全是等 IO 的。再看 `vmstat`：

```
$ vmstat 1 5
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 1 14      0 892144  41220 2201888    0    0  1840  3920 1204 2310  9  1 78 11  0
```

`r` 列是 1，`b` 列是 14。**真正在跑的只有 1 个，剩下 14 个在阻塞队列里。** 负载 21 里绝大部分是 `b` 贡献的，跟 CPU 一点关系没有。磁盘在扛，CPU 在闲。

## Linux 和 BSD 的老分歧

这里有个历史包袱值得说清楚，否则你在网上会看到两套互相矛盾的解释。

BSD 系的负载只统计 runnable 进程，IO 等待不算。Linux 从很早的版本起就把 `TASK_UNINTERRUPTIBLE` 也算进去了，理由是"这些进程迟早要用 CPU，现在压着它们的是别的东西，那也是系统压力"。两种口径都自洽，但含义不同。所以同一台机器，在 Linux 上看负载 20，在 BSD 上可能只有 2，谁都没撒谎。

这也解释了一个常见困惑：容器里 `uptime` 显示的负载为什么跟自己毫无关系。因为 `/proc/loadavg` 是内核全局的，宿主机上几十个容器共享一份，你看到的是整台物理机的排队情况，你自己的 cgroup 可能只分到 0.5 个核。容器里负载高，先确认是不是邻居在吵，别急着优化自己的代码。

## 负载高的四种来源，怎么分开

负载上去了，先别猜，按来源分四类：

**一，真的 CPU 不够。** `r` 列大于核数，`us + sy` 占比高，`wa` 接近零。这种是纯粹算力不足，加核、降并发、或者优化热点代码，方向明确。

**二，IO 卡住。** `b` 列大，`wa` 高，`D` 状态进程一堆。方向是查磁盘：`iostat -x 1` 看 `%util` 和 `await`。`%util` 长期贴着 100 不是"磁盘满了"，是"队列一直在排队"。云盘还有 IOPS 和吞吐的上限，超了就是等，跟容量没关系。

**三，内存紧张引起的连锁。** 内存不够会触发直接回收，进程在分配内存时被卡住，一样进 `D` 状态。这时候 `free` 看着"还有 cache"，实际可用（`available`）已经很低，swap 在频繁进出。负载高但磁盘不忙、CPU 不忙，多半是这条。我这台 7.5G 内存的机器就踩过，OOM Killer 挑最大的进程开刀，恰好是网关进程，一晚上断了两次。

**四，锁和网络文件系统。** `NFS` 服务端不响应，客户端所有碰这个挂载点的进程全部进 `D`，而且 `kill -9` 都杀不掉——信号要等系统调用返回才能投递。这类故障最难查，因为本地一切正常。

**五，云主机被邻居抢了 CPU。** `top` 里那一列 `st`（steal time）是被虚拟机监控器挪给别人用的时间。`st` 长期超过 5%，说明你这台实例的物理核被超卖了，负载高、响应慢，你在系统里查不出任何进程有问题。这种情况只能换实例规格或者换宿主机，调参是白费力气。云上排查，`st` 这一列永远要一起看。

## 我现在的判断顺序

看到负载告警，我不再看那三个数字，先看三个东西：

1. `nproc` 拿核数，`vmstat 1` 看 `r` 和 `b`。`r` 高是算力问题，`b` 高是等待问题，一句话分出方向。
2. `top` 里看 `wa` 和 `id`。`id` 高而负载高，基本可以确定不是 CPU。
3. `ps -eo state,pid,comm | awk '$1=="D"'`，把卡住的进程名字认出来。名字往往直接告诉你答案：`jbd2` 是文件系统日志，`mysqld` 是刷盘，`nfsd` 是网络存储。

这套顺序比"负载超过核数就扩容"省事得多。扩了核，`b` 队列照样堵着，钱花了，负载不掉，人还得再查一遍。

那个"8 核看 8"的经验阈值也别当铁律。它只对纯 CPU 密集型负载成立，而且 1 分钟的平均值本来就会因为一次批量任务短时冲高。真要设告警，看 15 分钟的平均值更稳，短时间的尖峰留给业务自己消化。

**负载是排队的人数，CPU 使用率是收银员有多忙。** 一个收银员闲着、门口排了二十个人的店，问题不在收银员的速度，在于有人把秤卡住了。数字不会骗人，是给它配错了单位。
