# 时间戳不是时间：一段耗时算出了负数

前段时间一个采集脚本的日志里出现了这么一行：

```
fetch done, elapsed = -3.2s
```

耗时是负数。脚本本身没崩，数据也拉全了，就是这行统计难看。我第一反应是加减法写错了，翻代码一看，就三行：

```python
start = time.time()
do_something()
print("elapsed = %.1fs" % (time.time() - start))
```

没有任何花活。唯一的可能是：这中间系统时间被改过，而且往回改了。

查下来果然，机器上开着 NTP 对时，那天这台机器的时钟快了 3 秒多，同步服务一把给拽了回来。脚本正好跨在这个窗口里，于是"结束时间"比"开始时间"还早。

这件事让我把时间这个事认真理了一遍：**时间戳不是时间，它只是一个标签。它回答"这是哪一刻"，不回答"过了多久"。** 混用这两件事，是工程里最常见、也最不容易被当回事的一类错误。

## 时间戳里到底存了什么

Unix 时间戳的定义是：从 1970 年 1 月 1 日 00:00:00 UTC 起，经过的秒数。就这一个数。

```bash
$ date +%s
1762300812
$ date -d @1762300812
Wed Nov  4 08:00:12 CST 2026
```

有意思的地方在这里：`1762300812` 这个数字本身，**不含任何时区信息**。它描述的是同一颗地球上的同一个瞬间。你觉得它对应"早上八点"，是因为你的机器时区设成了 CST（UTC+8）。把同一串数字拿到伦敦的机器上，`date -d` 会打印凌晨零点。数字没变，含义没变，变的只是显示。

所以那套"存 UTC、显示时转本地"的规矩不是洁癖。数据库里存本地时间字符串，等于把一个可以换算的瞬间，压成一句只在特定地区成立的话。等哪天服务器换机房、或者用户跨时区，这句话就没法翻译回去了。

还有个更细的坑：时间戳**不含闰秒**。Unix 时间是按每天 86400 秒均摊的，闰秒发生时系统通常选择"这一秒重复一次"或者"时钟慢一点走过去"，时间戳本身不会出现 23:59:60。也就是说，它连"物理上连续的时间"都不完全等于——它是一条为了方便计算而被拉直了的线。

## 墙上时钟会跳，单调时钟不会

区分两个东西：

- **墙上时钟**（wall clock）：`time.time()`、`date`、`NOW()`。它的任务是"我知道现在是几点"，而这个任务决定了它必须**可以被修改**——对时、手动改、虚拟机恢复快照，都会让它跳。
- **单调时钟**（monotonic clock）：`time.monotonic()`、`clock_gettime(CLOCK_MONOTONIC)`、Java 的 `System.nanoTime()`、Go 的 `time.Since()`。它的任务只有一个：**一直往前走，不回头**。它的起点毫无意义（可能是开机那一刻），你也别拿它去格式化日期。

一句话分工：**问"什么时候"，用墙上时钟；问"多久"，用单调时钟。**

Python 3.3 之后 `time.monotonic()` 是标准做法，`time.perf_counter()` 精度更高、专门用来测短耗时。上面那段代码改成这样，NTP 再怎么拽时钟也不会算出负数：

```python
start = time.perf_counter()
do_something()
print("elapsed = %.1fs" % (time.perf_counter() - start))
```

最典型的翻车场景不是脚本，是**限流和缓存**。用 `time.time()` 存"这个令牌什么时候过期"、"这个响应缓存到几点"，一旦时钟被往回拨，过期判断就会把已经过期的东西当成还有效，或者把刚写进去的缓存立刻判死。这类 bug 出现的概率很低，出现的时刻又总是在对时、迁移、容器重建这些本来就紧张的时候，所以极难查。

## 那个数还有自己的寿命

32 位有符号整数能表示的最大秒数是 2147483647，对应 **2038 年 1 月 19 日 03:14:07 UTC**。过了这一秒，`time_t` 溢出，回绕成 1901 年。这不是段子，很多跑了十几年的嵌入式设备、老数据库、老 C 库还在用 32 位时间。

顺带一提精度。秒级时间戳在日志里排序够用，但要给事件排序就不够了——同一秒里可能进来几百条请求，谁先谁后分不出来。这时候要么上毫秒、微秒，要么干脆给每条记录一个单调递增的序号，别指望时间给你排序。用时间戳当主键更是自找麻烦：它不唯一，也不保证递增。

还有定时任务。cron 写 `30 2 * * *`，看着是"每天两点半"，实际上依赖本地时区。碰上夏令时切换那天，两点半可能不存在，也可能出现两次，任务就漏跑或者跑两遍。所以关键任务的时间点，最好写成"UTC 几点"，或者干脆用"距上次成功执行多久"来判断，而不是死磕一个钟点。

## 我现在的三条习惯

**一，日志里同时写两个时间。** 人看的那行用带时区的 ISO 格式（`2026-11-04T08:00:12+08:00`），机器算的那列用 UTC 时间戳。带偏移量的写法最省事，谁看都不用猜。

**二，测耗时一律用单调时钟。** 不光是性能统计，重试间隔、超时判断、连接保活，只要涉及"过了多久"，就不用墙上时钟相减。这条改起来只要几分钟，能省掉一整类只在特定时刻发作的诡异故障。

**三，把时间当外部输入，不当常量。** 它会被改、会跳、会有精度限制、有寿命终点。凡是从系统时钟读来的值，都得当成"可能不准、可能倒退"的数据来用，而不是当成物理定律。

绕回来，那行 `elapsed = -3.2s` 其实是个挺诚实的报错。它没有骗我，它只是把我一直默认的一件事抖了出来：我以为我在测时间，其实我在数一个会被别人改掉的数字。

时间一直在往前走，时间戳不一定。这两件事分清楚了，很多莫名其妙的 bug 就自动少了一半。
