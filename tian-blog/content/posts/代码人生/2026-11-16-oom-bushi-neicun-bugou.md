# OOM 不是内存不够：Linux 先给承诺，后算账

半夜两点，一台机器上的服务没了。登上去看，第一眼是好的：

```
$ free -m
               total        used        free      shared  buff/cache   available
Mem:            7663        5210         612          18        1841        2243
Swap:           2047         2047           0
```

`available` 还有两千多兆。两千多兆，够跑一个中等服务了。可它偏偏在那之前被杀掉了，日志里只有一行：

```
Out of memory: Killed process 14873 (python3) total-vm:8563212kB, anon-rss:6120444kB,
file-rss:0kB, shmem-rss:0kB, UID:0 pgtables:12004kB oom_score_adj:0
```

这句内核日志，很多人读到"内存不足"就停了。但请注意它写的三个数：虚拟内存 8.5G，实际驻留 6.1G，机器一共 7.6G。**它不是"没内存了"才死的，是"欠的账还不上了"才死的。**

这是本文唯一想讲清的一件事：Linux 的内存管理不是一手交钱一手交货，而是先签支票、后兑付。所谓 OOM，是兑付窗口前排到了你，不是仓库空了。

## 内存是承诺，物理页是现金

进程调 `malloc(2GB)` 的时候，内核几乎立刻就答应了，返回一个地址。这时候一个物理页都没给它，页表里是空的。等到进程真的往这块地址写第一个字节，CPU 触发缺页异常，内核才慌慌张张去找一个空闲页填进去。

这个设计叫延迟分配，好处是省：一个申请了 8G 缓冲、实际只用了 200M 的程序，只花 200M。代价是，**申请成功和拿到内存是两件事**。前者是签支票，后者是兑付。中间隔着很长一段时间，也隔着很大的风险。

所以看到一个进程"吃掉了 6G"，跟它"申请了 20G"，完全是两种故障。前者是它真的占了，后者是它开了一张可能永远兑现不了的支票——只不过在某个瞬间，它同时要求兑付，而机器上已经凑不出这么多现金了。

`vm.overcommit_memory` 就是控制"允不允许超卖"的开关：

- `0`，启发式。内核对每笔申请做个粗略估算，明显离谱的（比如一次要 100G）拒掉，其余放行。默认值。
- `1`，永远答应。你要多少给多少，反正兑现不了的时候再说。Redis 的文档就建议这么配，因为它 `fork` 出来的子进程靠写时复制，实际占用远小于申请量，严格审核反而会挡住它。
- `2`，严格。按 `CommitLimit` 卡死，一分不许超。看着最安全，实际上经常让正常的程序 `fork` 失败，因为按"申请量"算账本来就是错的账。

三种模式都不是"正确"的，它们只是三套不同的赌法。

## free 那一列最小，恰恰最不重要

回到开头那张 `free -m`。六列里，只有 `available` 是给"我还能再要多少"这个问题准备的。

`free` 是"完全没被碰过的页"，Linux 会主动把空闲内存拿去缓存磁盘内容，所以这个数长期很小，甚至接近零——那是缓存干得好，不是内存紧张。`buff/cache` 那一千八百多兆，绝大部分是文件页，随时可以丢，丢了不会丢数据，只是下次读盘慢一点。

有人看到 `free` 只剩几百兆，第一反应是 `echo 3 > /proc/sys/vm/drop_caches`，把缓存全清掉，看着舒服了。这是典型的负优化：清掉的缓存，下一个请求还得从磁盘再读一遍，白白多一轮 IO；而真正导致 OOM 的那部分匿名内存，一个字节都没少。

`available` 才是内核给的估算值，它在 `free` 的基础上，加上可回收的缓存，再减去一些不可回收的部分（比如部分内核对象、无法换出的页）。两千多兆的 `available` 配上已经用光的 2G swap，这个组合说明当时的处境比看上去紧得多。**swap 已经是零，意味着内存回收的最后一个缓冲垫也垫完了。**

## 内核挑的不是罪魁，是最肥的那个

OOM killer 出场的时候，内存已经挤到极限，必须杀掉点什么才能让系统活下来。它按 `oom_score` 选人，而这个分数基本就是"你占了多少内存"：占得越多，分数越高，越容易被选中。

这就导致一个非常常见的错案：真正吃内存的是 A，但 A 分了很多次小批量地要，每次都在配额边缘徘徊；B 是个无辜的守护进程，刚好那一刻占得最多。内核没有业务概念，它只看见谁肥。**被杀的不一定是凶手，可能只是现场最显眼的那个人。**

唯一的干预手段是 `oom_score_adj`，范围 `-1000` 到 `1000`。往负数调需要 `CAP_SYS_RESOURCE` 权限，普通用户只能往大了调：

```
$ cat /proc/14873/oom_score_adj
0
$ echo -500 > /proc/14873/oom_score_adj
```

`-1000` 是"无论如何别杀我"，`1000` 是"优先杀我"。我自己那台 7.5G 的小机器上，网关进程就被误杀过一次——不是它吃的，但它正好在那时候最肥。后来给它设了 `-500`，加了 2G swap 当缓冲，才安稳下来。systemd 里可以直接写进 unit：

```ini
[Service]
OOMScoreAdjust=-500
```

这个值不是"保险"，是"降低被误伤的概率"。真到了全都不够用的那天，内核照样会动手，只是它会更倾向于杀那个真正肥的。

## 容器里 OOM，宿主机却内存充足

这是另一个高频谜题。容器里的进程被杀了，登到宿主机上一看 `free`，还剩好几个 G。

原因在于容器有两层限制。进程看到的是整台机器的内存（除非你开了别的视图），但它实际被套在 cgroup 的额度里。cgroup v2 下：

```
$ cat /sys/fs/cgroup/app.slice/memory.max
2147483648
$ cat /sys/fs/cgroup/app.slice/memory.current
2146918400
$ cat /sys/fs/cgroup/app.slice/memory.events
low 0
high 0
max 128
oom 3
oom_kill 3
```

`memory.max` 2G，`memory.current` 已经贴到 2G 的边缘，`oom_kill 3`——杀过三次。宿主机的富余跟这个 cgroup 一点关系都没有，它有自己的账本。**在哪一层设的限额，就在哪一层算账。**

顺带说清 `memory.high` 和 `memory.max` 的区别，这两个经常被混用：`memory.high` 是软上限，越过了内核不会杀你，只会开始强力回收、给你限速，进程表现为突然变慢；`memory.max` 是硬上限，越过了就直接 OOM。想"限一限但别杀"，用 high；想"绝对不能超"，用 max。很多人只设了 high 发现没起作用，是因为它的效果是"变慢"，不是"拦住"。

还有一个细节值得记：排查 cgroup 内存不能只看 `memory.current`，得看 `memory.stat` 里的构成。`file` 那部分是页缓存，可回收，算进 current 但不构成压力；真正顶死额度的是 `anon`。一个 2G 的容器里 current 显示 1.9G，如果其中 1.5G 是 file，那它其实很健康，只是读了不少文件。

## swap 不是慢内存

最后一个误解。很多人把 swap 理解成"内存的降级版"，觉得一旦用上 swap 就是性能灾难，于是 `swapoff -a`。

swap 的正面作用是给内核争取时间：内存紧的时候，把长期不碰的匿名页挪到盘上，腾出来的物理页给热数据用，让回收有节奏地进行，而不是一到顶就炸。它是个缓冲垫，不是替代品。真的灾难是"swap 用满了，物理内存也满了，回收不回来"，那才是账彻底兑不了。

我自己那台机器加 2G swap 之后，OOM 从"每周来一次"变成了"再没出现过"，代价是偶尔有点磁盘 IO。这笔买卖在内存小的机器上非常划算。有条件的话 `zram` 更划算——用压缩后的内存当 swap，速度比磁盘快一个量级，压缩比通常能到 2:1 以上。

## 怎么算预算，而不是猜

内存问题之所以难查，是因为它不像 CPU，没有一条平滑的曲线，只有一个突然的悬崖。我的做法是三件事：

第一，按峰值算，不按平均算。一个任务平均用 2G，但如果它要读一个 3G 的文件做一次排序，峰值就是 5G 以上。平均数是给报表看的，峰值才是给内存看的。

第二，能分批就分批。数据量一大，一次性读进内存是最省事也最容易炸的写法。切成一千条一批，内存占用立刻从"跟数据量成正比"变成"跟批大小成正比"，代价只是多几次循环。**内存问题最好的解法往往不在内存参数里，在循环怎么写里。**

第三，给关键进程留后路。`OOMScoreAdjust` 保护值守进程，cgroup 的 `memory.max` 给业务留出余量（设成物理内存的八成，剩下两成是给页缓存和内核的），swap 当缓冲垫。这三件事花不了十分钟，但能把"半夜被叫起来重启服务"变成"早上看一眼监控"。

回到那句内核日志。`Out of memory` 说的从来不是"这个仓库没货了"，而是"这个柜台同时来兑付的人太多，我付不出"。仓库里还有多少货，得看 `available`，看 cgroup 的额度，看 swap 还剩多少，看你到底签了多少张还没到期的支票。

**内存焦虑的根源，是只盯着余额，不盯着欠条。**
