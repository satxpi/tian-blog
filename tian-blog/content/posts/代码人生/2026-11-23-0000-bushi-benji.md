# 0.0.0.0 不是本机地址，是“所有门都开”

服务起好了，日志一片绿。我在服务器上 `curl 127.0.0.1:8000`，通，返回正常 JSON。打开浏览器输 IP 加端口，转圈，最后超时。翻回去看启动日志，那一行明明写的是 `Uvicorn running on http://0.0.0.0:8000`。

这类问题我见过很多次，方向也五花八门：安全组、防火墙、反代配置、证书、浏览器。但真正让我在原地停了半天的，是那个 `0.0.0.0`——我一直以为它只是"本机"的另一种写法，跟 `127.0.0.1` 差不多，随便用哪个都行。

后来才把这件事想清楚：**在网络里，地址不是机器的名字，是网卡上的一个编号。你监听哪个编号，就等于决定坐在哪扇门后面等人。** 这一句话能解释掉一大半"本地通、外面不通"的故障。

## 127.0.0.1 这条路，压根不出门

先说那个真的只属于本机的地址。

`127.0.0.0/8` 整段都是回环地址，一共一千六百多万个，全部指向"我自己"。发往 `127.0.0.1` 的包不进网卡队列，不上网线，也不经过交换机，它走的是内核里一条虚拟回路：协议栈把包造出来，看一眼目的地址是回环网段，直接放回自己的接收队列。整个旅程在内存里完成，耗时是微秒级。

这个设计的后果很直接：**物理上不可能有外部的包到达 `127.0.0.1`**。所以一个只监听 `127.0.0.1:6379` 的 Redis，即使你把防火墙全拆了、安全组全放开、把公网 IP 直接贴给它，外面也连不进来。挡住的不是墙，是这条路本身不存在。

这也是很多服务默认绑回环的原因。MySQL 的 `bind-address` 默认是 `127.0.0.1`，Redis 的 `protected-mode` 配着 `bind 127.0.0.1`，都是从同一个判断出发的：这东西不打算给外人用，那就别把门开在路上。反过来，互联网上被扫得最快的端口里，`0.0.0.0:6379` 常年排在前几——不是 Redis 不安全，是有人把它从后厨搬到了大门口。

顺带一个冷知识：`127.0.0.53` 在 Ubuntu 上被 `systemd-resolved` 占着，`127.0.0.1` 旁边那个 `127.0.1.1` 常常被写进 `/etc/hosts` 当主机名用。整段 `/8` 都是本机，所以怎么写都能通，写错也没人发现。

## 0.0.0.0 不是地址，是"任何"

这是最容易误解的地方。

`0.0.0.0` 在 `bind()` 的语义里叫 `INADDR_ANY`。它不是一个可以写进信纸的收件地址，它的意思是"**本机上任何一个 IPv4 地址，都算我的**"。

区别在这儿：你绑 `127.0.0.1`，内核的监听表里就记一条"127.0.0.1:8000"；你绑 `0.0.0.0`，记的是"任意:8000"。包进来的时候，内核按目的地址去查这张表，先找精确匹配，找不到再找通配的那条。所以监听 `0.0.0.0` 的服务，本机访问 `127.0.0.1` 能进，局域网访问 `192.168.x.x` 能进，公网访问那个弹性 IP 也能进——三扇门后面坐着同一个人。

有一个特别能说明问题的现象：**同一个端口，可以同时被两个"具体地址"监听，但不能和 `0.0.0.0` 共存**。你在 `127.0.0.1:8080` 起一个，在 `192.168.1.5:8080` 再起一个，两个都成功，各接各的客户。但只要有一个占了 `0.0.0.0:8080`，任何具体地址再来绑同一个端口都会报 `Address already in use`（除非显式开了 `SO_REUSEPORT`）。这条冲突规则本身就是证据：地址不是端口的附属品，它是监听资源的一半。

另外，`0.0.0.0` 不能用来连。你不能 `curl 0.0.0.0:8000` 之外还指望它有别的含义，也不该把它写进配置文件当目标地址。它是"绑定的语法"，不是"连接的目的地"。

## localhost 是个名字，名字会撒谎

`localhost` 更麻烦，因为它看起来最无害。

它根本不是地址，是一个需要在运行时解析的名字。解析走 `/etc/hosts`，很多系统里那份文件长这样：

```
127.0.0.1   localhost
::1         localhost ip6-localhost
```

两行都叫 `localhost`。`getaddrinfo()` 返回的结果是一个列表，先试哪个取决于系统的地址排序规则（RFC 6724）。不少环境里 `::1` 排在前面。

于是就出现了那种让人抓头的现象：服务只监听了 `0.0.0.0`（纯 IPv4），`curl 127.0.0.1:8000` 通，`curl localhost:8000` 报 `Connection refused`。不是服务挂了，是客户端先敲了 IPv6 那扇门，没人应，然后放弃了——行为取决于客户端有没有做 Happy Eyeballs 式的回退，`curl` 和浏览器、和 Python 的 `requests`，表现都不完全一样。

反方向的坑也存在：`ss -lntp` 里看到 `[::]:80`，容易以为"这只接了 IPv6"。但 Linux 上 `net.ipv6.bindv6only` 默认是 0，一个绑在 `::` 上的 socket 默认也接 IPv4（映射成 `::ffff:0.0.0.0` 那种形式）。所以 `[::]:80` 往往两头都吃，而 `0.0.0.0:80` 只管一头。这个默认值坑过不少人，也解释了一堆"我明明只开了 v6 怎么 v4 也能连"的困惑。

## 容器里的 127.0.0.1 是谁

到了 Docker，这个问题会变得更绕，因为 `127.0.0.1` 所属的"本机"变了。

每个容器有自己的 network namespace：一套独立的路由表、独立的 `lo`、独立的 `eth0`（通常是一对 veth，一头在容器里，一头挂在宿主的 `docker0` 网桥上）。**容器里的 `127.0.0.1` 是容器自己的回环，不是宿主机的。**

所以那个经典故障是这么来的：容器里的应用监听 `127.0.0.1:80`，宿主机上 `-p 8080:80` 也加了，外面还是连不上。原因是端口映射的实现是 NAT——宿主机的 `iptables` 在 `PREROUTING` 阶段做 DNAT，把目的地址从"宿主机 IP:8080"改成"172.17.0.2:80"，包从容器 `eth0` 进来，目的地址是 `172.17.0.2`。而容器里那个 socket 只认 `127.0.0.1:80`，目的地址对不上，内核直接回 RST。`docker-proxy` 那条用户态转发路径也一样，它连的是容器 IP，不是容器回环。

结论很硬：**容器里的服务要对外，必须监听 `0.0.0.0`（或容器自己的 IP），监 `127.0.0.1` 等于把门开在一个谁也到不了的院子里。**

同一个原因，反着也成立：容器里想访问宿主机的服务，不能写 `127.0.0.1`，那指的是容器自己。要写宿主在 `docker0` 上的地址（一般 `172.17.0.1`），或者用 `host.docker.internal`（Docker Desktop 默认有，Linux 上要加 `--add-host` 或 `host-gateway`），干脆用 `--network host` 把命名空间合并；合并之后，`127.0.0.1` 就又是同一个了。

这套东西一旦想通，Kubernetes 里 `Service` 的那层 VIP、`kubectl port-forward` 为什么能生效、sidecar 为什么能拦流量，都能顺着同一根线捋下去：**"本机"从来不是一台机器，是一个命名空间。换一个命名空间，`127.0.0.1` 就换了一个人。**

## 防火墙管外，不管里

还有一个常见的误判：以为"本机能连上"就说明服务健康、网络通畅。

云厂商的安全组、宿主机上的 `iptables`，管的是"从外面进到你这里"的包。回环流量虽然也走 `INPUT` 链（它确实是进本机的），但不经过 `PREROUTING`，也不出网卡，安全组更是一点关系都没有。所以一个端口在安全组里全封着，本机 `curl 127.0.0.1` 照样通；而一个服务对外完全正常，本机 `curl` 也可能因为 `Host` 头、SNI、反代的 `server_name` 匹配不上而返回 404 或者 502。这两件事压根不是同一个层面。

顺便说，`iptables` 的 `INPUT` 链如果被写成默认 `DROP` 而又没放行 `lo`，那本机连自己都会连不上。多数发行版的规则集里有一行 `-A INPUT -i lo -j ACCEPT`，就是为了这个。它不是装饰，缺了它整套本机通信会静默断掉——而排查的时候，人会先怀疑应用，最后才怀疑那条规则。

## 一份够用的判断表

真正实用的不是背原理，是把 `ss -lntp` 的那一列看懂。`Local Address:Port` 有四种，意思完全不同：

- `127.0.0.1:8000` —— 只有本机能连。要对外，就配 SSH 隧道（`ssh -L 8000:127.0.0.1:8000 user@host`）或让 nginx 反代，别改绑定。
- `0.0.0.0:8000` —— 所有 IPv4 网卡都接。要限流，靠防火墙和安全组做减法。
- `192.168.x.x:8000` —— 只接那一张网卡，内网能用，公网多半不行。
- `[::]:8000` —— IPv6 通配，Linux 默认连 IPv4 一起接（`bindv6only=0` 时）。

三件事按顺序做，基本不会误判：先 `ss -lntp` 确认绑的是哪个地址，再确认客户端实际解析到哪个地址（`getent hosts localhost`、`curl -4` / `-6` 分别试），最后才去看防火墙和安全组。顺序反了，就会在安全组里翻半小时，而问题在第一行日志里。

回到开头那次。`0.0.0.0:8000` 明明是开的，外部还是不通，最后查到是前面还有一层 nginx，`proxy_pass` 写的是 `http://127.0.0.1:8001`——差了一个端口号。跟 `0.0.0.0` 一点关系都没有。但也正因为我把 `0.0.0.0` 和 `127.0.0.1` 当成了同一个东西，前面那半小时全花在错的地方。

**地址是门牌，监听是决定坐在哪个门牌下面等人。网络里没有"本机"这个抽象概念，只有"哪个命名空间里的哪张网卡上的哪个地址"。** 想清楚这一层，很多听起来玄的故障就变成了查表。

*个人观点，请多包涵。*
