# sudo 不是把我的权限放大，是把我换成了另一个人

前几天在服务器上跑一个脚本，生成当天的数据文件。脚本要往几个系统目录里写东西，我顺手在命令前面加了 `sudo`，回车，日志一行行刷过去，一切正常。

第二天我回来改脚本，`vim` 打不开它昨天生成的那个文件，存盘报 `Permission denied`。

同一条命令，前后两副面孔。我打了个 `ls -l`：

```
-rw-r--r-- 1 root root 48213 Oct 13 07:12 daily.csv
```

两个 root。不是"当时我有 root 权限"，而是**这个文件从此属于 root**。

## sudo 不是放大镜，是换人

我一直把 `sudo` 当成一个放大镜：同一个我，临时把权限调大一点，做完事收回来。直到看见那两个 root 才想明白，它不是放大镜，它是换人。

`sudo` 干的事情非常直白：**换一个用户身份，再来执行这条命令**。默认换成 root，于是执行它的那个进程 uid 就是 0，进程创建的文件，主人自然就是 root，跟发起命令的人没关系。它不管你是谁、加了多少年的班、有多熟这台机器。

所以 `sudo` 从来不带"临时"两个字。**权限是借的，所有权是留下的。** 命令跑完，权限收回去了，文件的归属留在原地——留下的这部分，才是第二天麻烦的来源。

## 同一个 sudo，还有两套环境

文件所有权是最容易撞见的一层，但它不是唯一一层。用久了会发现，`sudo` 之后的那个世界，跟平时不是同一个：

- **`~` 指的可能是别人的家目录**。sudo 之后 `HOME` 常常被切成 `/root`，脚本里一句 `output_dir = "~/data"`，文件就悄悄落到了 `/root/data`，我在自己家目录下翻半天都找不到。
- **`which python3` 给的是另一个答案**。普通用户下的 PATH 里可能有虚拟环境的路径，sudo 之后 PATH 被重设，找到的是系统那个 `/usr/bin/python3`。同一条命令，两套依赖，一边能跑一边报找不到模块。
- **环境变量大半没跟过来**。我平时在 `~/.bashrc` 里导出的代理、密钥、路径，sudo 之后多半不生效，脚本里读到的全是空值。

这些都是同一件事的不同侧面：**sudo 换的不只是权限，是整套身份——家目录、PATH、环境变量一起换。**你写脚本时默认"我"存在，sudo 之后那个"我"其实已经不在了。

## 更隐蔽的一份：crontab 也是两份

还有一处更容易栽。机器上有定时任务，我改过之后第二天发现改动没生效，翻了半天文件时间戳，最后才想起来：`sudo crontab -e` 编辑的是 **root 的**定时任务表，`crontab -e` 编辑的是 **我自己的**，这是两份完全独立的表，互不覆盖、互不冲突，也互不提醒。我改了一份，跑的是另一份。

定时任务还有第二层：root 的 cron 跑起来时，环境是精简版的，PATH 短得可怜，平时敲得好好的命令会报 `command not found`。我那时候的解法很笨也很实在——脚本里凡是外部命令，全写绝对路径。

## 那到底该怎么用

不是说别用 sudo，很多事情非它不可。我现在守几条：

**一、只在真的要动系统东西的时候用。** 写业务数据、生成报表、编译自己的项目，这些我都不加 sudo。自己该有的权限，就用自己的身份去用。

**二、必须用的时候，把归属交回来。** 跑完立刻 `sudo chown -R $(id -u):$(id -g) ./输出目录`，别等到第二天才发现手里一堆不属于自己的文件。

**三、要指定身份，就用能指定身份的方式。** 想让某个用户去跑，`sudo -u 用户名 命令` 比"整条命令都抬到 root"清楚得多，落下来的文件归属也对得上。

**四、别拿 sudo 去绕问题。** 我不会再为了省事用 `sudo pip install`，因为它会把包装进系统 Python，跟我的虚拟环境彻底脱钩——当时看着能跑，其实是在给以后的自己挖坑。文件权限报错，宁可停下来看两秒 `ls -l`，也不顺手加个 sudo 盖过去。

## 说到底

`sudo` 这个词读作 "superuser do"，但它的语义其实是 "as another user"。它不给我加特权，它把我换了个人：换个人去执行、换个人的环境、换个人的家目录，还顺手把产出的东西登记在那个人的名下——只有我没换。

想清楚这一层之后，我在服务器上敲命令的手会停半秒：这条命令我看得懂，但**执行它的那个人，是不是我**。

*个人观点，请多包涵。*
