# 我让AI重构老代码的三十天：哪些干得漂亮，哪些翻车了

过去一个月，我做了个实验：把手上一个写了三年的老项目，交给AI去重构。三十天下来，有真香的时刻，也有摔跟头的时刻。今天把这三十天的经验如实写出来，给想用AI重构代码的同行一个参考。

## 先说结论

**AI重构，三成干得漂亮，七成需要人盯着。** 它最擅长的不是"重写"，是"填空"——你把边界画清楚，它把里面的活干完。但你要是撒手让它自己来，它能把你的代码库变成它自己的风格，然后留下一堆你没看过的"魔法"。

## 干得漂亮的：重复代码清理

这个项目里有一堆几乎一样的函数——三个接口各自写了一套类似的参数校验，改了A忘了B是常态。我把三个函数的代码丢给AI，说"合并成一个，保持行为不变"。它干的活堪称完美：抽了公共逻辑，保留了各自的特例，还补了单元测试。

**为什么能干好？** 因为"合并重复代码"是一个边界极其清晰的任务——输入、输出、行为都明确，AI只要做等价变换。这类活，AI比人快十倍，而且不容易漏。

## 翻车现场：盲目升级依赖

我让AI"把项目里过时的依赖升级到最新版"。它照做了——然后项目跑不起来了。

为什么？因为它升级了十几个包，却没有处理这些包之间的兼容性：A包新版本换了API，B包又依赖A的旧接口……它把每个包都"正确地"升了级，但组合起来就崩了。

**教训：** 涉及全局状态的改动（依赖升级、配置迁移、数据格式变更），AI做不好。它看不到整个生态的耦合，只看到眼前这一个文件。

## 翻车现场二：它爱上了自己的重构

我让它重构一个核心模块，强调"保持对外接口不变"。它确实做到了——接口没变，但内部逻辑被它"优化"得面目全非，我花了整整两天才确认行为确实没变。

**教训：** AI重构后，你必须review每一行它改过的逻辑，尤其是核心路径。它写的新代码不一定错，但**你没看过的代码，就是你的技术债**。

## 哪些活适合AI，哪些不适合

| 适合 | 不适合 |
|------|--------|
| 合并重复代码 | 全局依赖升级 |
| 补单元测试 | 核心算法重写 |
| 重命名/提取函数 | 数据迁移 |
| 按规范格式化 | 架构级重构 |
| 写文档注释 | 你不知道要什么的重构 |

**核心判断标准：你能不能画清楚边界？** 边界清楚（输入输出行为明确），AI就靠谱；边界模糊（"把它弄好一点"），AI就会自由发挥，然后你来收拾。

## 我的工作流（现在固定这样用）

```
1. 先自己看代码，明确"要改成什么样"
2. 写清楚边界: 输入、输出、行为约束、测试
3. 让AI改一个文件，马上review + 跑测试
4. 通过了再放它改下一个
5. 每次改动独立提交，随时能回滚
```

**永远不要让AI连续改超过一个文件而不review。** 这是我这三十天最大的教训——它连续改三个文件的时候，最后一个文件的质量明显下降，因为它的"上下文"已经被前面的改动污染了。

## 写在最后

AI重构代码，本质是**一个极快的、但需要监督的初级工程师**。你给它画好图纸，它能高效执行；你让它自己发挥，它能给你惊喜，也能给你惊吓。

用它的原则就一条：**边界你画，活它干，验收你来做。** 记住这条，AI是效率神器；忘了这条，AI是技术债制造机。

工具可以学，但代码是你的——重构完的每一行，你都得负得起责任。
