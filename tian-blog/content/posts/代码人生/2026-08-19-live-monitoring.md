# 没人盯盘的时候，系统得自己会喊救命

做量化的前两年，我把几乎所有精力都花在策略上：因子、回测、调参。那时候我有个朴素的想法——只要策略够好，赚钱是水到渠成的事。直到实盘系统出了几次事，我才明白一个反直觉的道理：**实盘交易系统真正考验人的不是策略，是"没人盯着的时候，它会不会自己喊救命"。**

先说一次让我印象最深的事故。

那是一个普通交易日，上午收盘后我例行打开账户看成交。奇怪的是，今天应该有五笔信号触发买入，账户里却只有两笔成交。再看日志，系统运行正常，没有报错，持仓也显示正常。我花了一个多小时翻代码、查 API 文档，最后发现原因：第三方券商接口当天更新了鉴权规则，我的 token 在凌晨就失效了。下单请求全部返回"未授权"，而我的代码把失败静默吞掉了——只写进日志，不抛异常，不告警，甚至不重试。于是系统表现得一切正常，只是什么都没买。

那笔漏掉的交易，正好赶上那波行情里最大的一根阳线。

这个教训值多少钱不好说，但它彻底改变了我的做事方式。**静默失败是实盘系统最贵的失败**——它不报错，不打扰你，只是安静地不干活。等你自己发现的时候，损失已经发生了。而它之所以可怕，恰恰因为"一切正常"恰恰是最正常的表象。

从那以后，我给自己定了一条规矩：**凡是实盘路径上的关键环节，都必须有独立的健康检查，检查结果必须有去处，去处的终点必须是人。** 具体落下来，是这么几件事。

**进程活着不等于系统活着。** 最开始我只看进程在不在，后来发现这远远不够。进程活着，可能卡在死循环里，可能连接池耗尽在等超时，可能数据源早就断了还在拿旧数据算。所以我不再"探活"，改成"探业务"：定时检查行情数据的最新时间戳，超过阈值就告警——数据不新鲜，意味着策略可能在用昨天的数据做今天的决策，这比系统崩溃危险得多。数据新鲜度检查，我现在放在所有监控的第一位。

**信号要对得上账。** 策略说要买五只，实际下了几单？这是我最在意的对账。每天收盘后跑一遍：策略生成的信号列表、实际下单记录、最终成交记录，三张表做差集，任何一笔对不上都要查清楚。这个对账脚本本身也要被监控——如果它今天没跑，本身就是一个告警。

**账户权益和持仓偏差要盯住。** 实盘账户和我的参考组合之间，权益差超过阈值、持仓偏离超过阈值，都说明执行出了岔子。这类检查的价值在于它不看内部日志，只看最终结果——日志可以撒谎，账户不会。

**双跑对账是最后的保险。** 同一套策略，模拟盘和实盘并行跑，两边信号一致才对。有一阵子我的模拟盘稳定盈利、实盘却总是差一截，双跑对账帮我定位到是下单时间戳的时区问题——模拟盘用的是本地时间，实盘用的是服务器 UTC 时间，差了八个小时，信号被贴到了错误的 bar 上。这种 bug 靠看代码很难发现，靠两边对照一眼就现形。

监控搭起来之后，紧接着的问题是告警本身。这里有个我踩过的坑：一开始我把所有异常都往同一个群发，结果群里一天几十条消息，真正的要命信号淹没在噪音里，我反而开始习惯性忽略。后来我改成分级：数据不新鲜、信号对不上账这种直接影响交易的，走电话和置顶群，立即处理；日志异常、指标抖动这种间接问题，走普通群，当天处理。**告警疲劳是真实存在的，分级不是偷懒，是为了保证重要告警发出时还有人看。**

还有一条更反直觉的经验：**告警要经常"演练"，甚至故意制造故障来测试它。** 我第一次主动把数据源断开测试告警，发现告警根本没发出来——因为监控脚本自己崩了，而监控脚本的崩溃没人监控。这就是监控的套娃问题，只能靠定期演练来兜底。现在我每个月挑一天，故意让系统出错，看看告警链路走不走得通。平时多演练一次，真出事那天就少慌一次。

回头看，这些工程活没有一个是"策略性"的，它们不产生 alpha，不会让回测曲线更好看。但它们决定了一个朴素的底线：**当系统出错的时候，你能不能第一时间知道，并且知道错在哪。** 策略决定你能赚多少，监控决定你会亏多少——后者往往才是实盘活下来的关键。如果你也在跑实盘，我建议从最小的闭环开始：先保证每笔交易都有日志、每个失败都有告警、每条告警都有人看。这三点做到，你的系统才算真正"上了线"。
