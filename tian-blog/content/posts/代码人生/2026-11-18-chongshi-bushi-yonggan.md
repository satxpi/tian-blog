# 重试不是勇敢，是把一次失败放大成二十七次

有个上传接口，偶尔会超时。频率不高，一天也就十几回，用户刷新一下就好了。我看日志看得心烦，就在客户端加了个循环：失败就再试，最多三次，间隔一秒。

改完当天下午，超时确实少了。晚上八点，那个服务挂了。

不是被流量打挂的。是被自己的重试打挂的。上游一个存储节点抖了两分钟，超时开始出现，我的三次重试立刻把请求量乘了三倍。那两分钟里，原本每秒两千个请求变成六千个，本来只是慢一点的节点，直接被压到拒绝连接。然后更多的请求失败，更多的请求重试。二十分钟后，整个链路都在重试，没有一个环节在干活。

这件事之后我才认真去想：重试到底在干什么。

## 它不是"再努力一次"，它是一次请求的复制

`for i in range(3)` 这种写法太顺手了，顺手到人会忘记它真正的语义：**每一次重试，都是一次全新的、完整的、带着全部副作用的请求。**

它不是一个"更用力"的请求，是三个请求。三个请求会同时出现在下游的连接池里、线程池里、队列里。下游本来就因为某种原因慢了，你给它的不是鼓励，是更多的活。

这就是重试最反直觉的地方：它在你这一层看起来是"提高成功率"，在下游看起来是"流量突增"。故障的时候，所有人一起重试，下游收到的不是一千个请求，是一万个请求，然后它彻底躺下，然后所有人都一直重试。

有一个乘法很多人算不清：如果你的 HTTP 客户端 SDK 默认重试 2 次，你的业务代码自己重试 3 次，中间的网关或 sidecar 再重试 2 次，那么一次用户点击，在最坏情况下会在后端变成 `3 × 3 × 3 = 27` 个请求。中间任何一层抖动一下，后面就是一个 27 倍的尖峰。

所以第一条规矩其实很简单：**重试只在一个地方做，而且只做一层。** 谁最清楚这次失败该不该重试，就让谁重试，其他层老老实实把错误往上抛。层层加码不是稳健，是把保险买了两份然后指望赔两次。

## 只有两种失败值得重试

重试能不能用，取决于两个条件，缺一不可。

第一个：**这个失败是瞬时的。** 网络抖动、连接被重置、下游刚重启还在预热、主从切换的那三秒——这些过一会儿确实会好。而参数错了、权限不够、资源不存在、签名不匹配，这些东西你试一百次，一百次都是同样的错。它们不会自己好。

第二个：**这个操作是幂等的。** 也就是重复执行一次，和只执行一次，结果一样。查一个订单是幂等的，删一个文件基本是幂等的，`PUT` 一个已知的完整状态是幂等的。而"创建订单""提交支付""发一条短信""追加一条日志"都不是。你重试三次，用户就收到三条短信、三笔扣款，或者数据库里躺着三条一样的订单。

第二个条件比第一个重要得多，因为它出问题的时候不报错。前面那次上传，我的接口本身是幂等的（覆盖写同一个 key），所以我只是把下游压死了，数据没错。可我见过更贵的版本：一个"下单"接口加了重试，客户端超时但其实服务端已经成功了，客户端重试，服务端再下一单。用户第二天来找，说买了两份。

所以顺序应该是反过来的：先证明操作幂等，再谈重试。证明不了，就别重试，改成"失败就明确失败，让用户自己决定要不要再来一次"。这不是偷懒，这是诚实。

按 HTTP 状态码分，判断标准大概是这样的：`429` 和 `5xx` 可以重试，`408`（请求超时）可以，连接层的 `ECONNRESET`、`ETIMEDOUT` 可以；而 `400`、`401`、`403`、`404`、`409`、`422` 一个都不要重试，重试它们只是浪费自己和对方的时间。DNS 解析失败、证书校验失败、连接被拒绝，这一类也别重试——这不是抖动，这是配置错了。

## 固定间隔的重试，是一颗定时炸弹

我最初那个版本是"间隔一秒"，这个细节后来被我认定是当天事故的第二个推手。

原因不难想：所有失败的请求是在同一秒开始失败的，它们也会在同一秒一起重试。第一秒失败一千个，第二秒同时来一千个，第三秒又是同时一千个。下游刚喘上一口气，立刻被同样的浪头再拍一次。这种整齐划一的节奏，比自己写个死循环还狠。

正确做法是指数退避加随机抖动。第 n 次重试等 `base × 2^n`，再乘一个 `[0.5, 1.5)` 之间的随机数。随机的意义不是好看，是把同一秒涌上来的请求摊平到一个时间窗里，让下游有机会恢复。AWS 那篇讲指数退避和抖动的老文章里有一句话我记到现在：抖动的作用是打破"同步"，而同步正是雪崩的燃料。

退避还有一层含义：如果下游需要三十秒才能恢复，你在一秒后重试五次，等于五次都没用，还多打了五份负载。等待本身就是一种资源投入，间隔要跟"对方大概多久能好"对齐，而不是跟"我有多急"对齐。

## 重试要有预算，不然是白干

这一条是最容易被忽略的。

假设上游（比如浏览器、或者你的调用方）的超时是 3 秒。你在 3 秒里重试三次，每次超时 2 秒——第一次就吃掉了 2 秒，第二次还没跑完，调用方那边已经超时返回了。你以为自己很努力，实际上做的全是无用功，而且是在对方已经放弃之后继续消耗资源。

所以重试必须挂在一个总预算下面：整条链路一共允许多少时间，重试用掉多少，剩下的留给业务逻辑。这个预算要一路往下传，而不是每一层各拍一个超时。gRPC 里有 deadline 传播，HTTP 里可以用 `grpc-timeout` 或者自定义头，道理都一样：**上面的耐心是有限的，下面的努力不能无限。**

还有些情况，重试本身就是错的。比如下游已经明确在限流（429 带 `Retry-After`），你这时候重试得越勤，被限得越久。比如下游健康检查已经不通过了，那你需要的不是重试，是熔断——先别发，等它缓过来。重试和熔断是一对：重试是在赌"再来一次就好了"，熔断是在承认"现在怎么来都不会好"。只会重试不会熔断的服务，本质上是在用下游的血给自己续命。

## 真的躲不开重试的时候

有些场景你没法不重试，比如消息队列、异步任务、跨机房的写。这时候的老办法是：把幂等做在业务里，而不是做在客户端。

给每个操作带一个幂等键（请求 ID、业务流水号），服务端准备一张去重表或者用 Redis 记一段时间内的键。收到了先查，查到了就直接返回上一次的结果，没查到才真正执行。同一个键来一百次，副作用也只发生一次。这样重试就从"危险动作"变成了"安全动作"，你可以放心地重试、放心地让它重试一夜。

代价是那张表要维护、要清理、要考虑并发下的写入冲突（一般是给键加唯一索引，让数据库去仲裁）。但这是必须付的钱。**要么把重试做成安全的，要么就别重试**——中间那条"差不多应该没问题"的路，通向的就是第二天早上用户发来的截图。

## 说到底

重试不是勇气，它是一道很窄的题：失败是瞬时的吗？操作是幂等的吗？间隔是散开的吗？预算是够的吗？四个都答"是"，重试就是好东西，能把偶发的抖动挡在用户看不见的地方。有一个答"不知道"，那重试就是在拿运气当设计。

我现在的写法，是先问自己一句："如果这次请求成功到达了对方，只是我没收到回执，会发生什么？"如果答案是"什么都不会多出来"，那就放心重试；如果答案是"用户会多付一次钱"，那就在重试之前，先把去重做出来。

那天晚上的事故，最后是靠把重试从三层砍到一层、间隔改成退避加抖动、再给下游加了一个熔断恢复的。加的东西比原来多，但请求量回到了该有的样子。**稳不是靠多试几次试出来的，是靠知道什么时候该停手。**
